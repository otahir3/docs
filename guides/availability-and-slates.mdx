This is the deep-dive companion to
[Create a package booking with a slate](/guides/create-a-package-booking). That
guide covers the primary flow — build a slate, create an order, book it by
`slateId` — end to end. This page goes underneath it: what the five
availability endpoints are for, exactly what a slate response contains, the
cadence rules that shape it, what happens when a supplier can't meet those
rules, and the two advanced booking paths that exist alongside
book-by-`slateId`.

It builds on [The booking engine model](/concepts/booking-engine-model) —
read the [Slates](/concepts/booking-engine-model#slates) section first if you
haven't.

## The availability engine

Five endpoints make up the availability engine, all authenticated with the
`x-api-key` header (see the table below for exact paths). They're layers of
the same clustering engine, from lowest to highest level:

| Endpoint | Use it when |
| --- | --- |
| `POST .../availability/time-slots` | You already hold the scheduling state (suppliers, their bookings, their availability) and want to run the engine directly, passing everything in the body. |
| `POST .../availability/search` | You have a service + offering + location and want the API to resolve suppliers from project data and return suggested/open slots — one-off, single-session slots. |
| `POST .../availability/suppliers` | You want the same single-session availability **grouped by supplier** — a paginated list of supplier profiles, each with its open slots bucketed by local day. Reach for it when rendering a wall of supplier cards. |
| `POST .../availability/package-slate` | You want a **complete N-session plan** for a package from one supplier, computed from a recurrence rule (`rrule`). This is the endpoint the rest of this guide covers. |
| `POST .../availability/package-options` | You want **every** ACTIVE package of a service planned in one call, each with its own ready-to-book `slateId`. The composite built on `package-slate` — reach for it when rendering a package storefront. |

<Note>
`/search`, `/time-slots` and `/suppliers` are documented in full in the
[Availability resource reference](/resources/availability) — request fields,
the recurring-search variant, and response envelopes. This guide focuses on
`/package-slate`, since it's the one with package-specific anatomy and the
two advanced booking paths below.
</Note>

## Anatomy of a slate

`POST /availability/package-slate` takes a `packageId` (the session count,
service, and offering are derived from it), a location, a `timezone`, and a
cadence (`lookAheadStartDate` + `rrule`). The response is a
`PackageSlateResponse`:

```json
{
  "status": "OK",
  "reason": null,
  "suggestionRequestId": "sugreq_01kx16ej7pe4r9da74adf6m4h0",
  "resolvableUntil": "2026-07-10T00:00:00.000Z",
  "primarySlate": {
    "slateId": "slate_01kx16ejsqffc9rbgdcc591w2p",
    "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
    "completeness": "COMPLETE",
    "sessionsRequested": 8,
    "sessionsFilled": 8,
    "startTimeConsistencyPercent": 100,
    "matchScore": 1,
    "matchComponents": { "startDate": 1, "cadence": 1 },
    "totalTravelTimeMins": 0,
    "slots": []
  },
  "alternates": [],
  "partial": null,
  "cadenceAlternatives": [],
  "requestedCadence": "FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;COUNT=8"
}
```

(`slots[]` abridged to `[]` here — see [Create a package booking](/guides/create-a-package-booking)
for a fully populated example, and the field tables below for its shape. `alternates` is shown
empty for brevity too — under the default `supplierPolicy` of `SAME_SUPPLIER` it carries this
same supplier's other bookable schedules.)

| Field | Meaning |
| --- | --- |
| `status` | `OK`, `ALTERNATIVE_CADENCE`, `NO_COMPLETE_SLATE`, or `NO_AVAILABILITY` — see below. |
| `reason` | Human-readable explanation when `status` isn't `OK`. `null` on success. |
| `suggestionRequestId` | Audit id for this request. Present only when `persist` is `true` (the default). |
| `resolvableUntil` | Slates and slots stay resolvable (holdable/bookable by id) for **24 hours** from the request; after that they're stale. |
| `primarySlate` | The best **COMPLETE** single-supplier slate — book this by `slateId`. `null` if none satisfies the project's supplier policy. |
| `alternates` | Other bookable options beyond `primarySlate`, ranked best first and capped at the request's `maxAlternates` (default `3`; `0` returns none). Under the default `supplierPolicy` of `SAME_SUPPLIER` these are other schedules from the same supplier as `primarySlate`; under `PREFERRED` or `ANY` they're other suppliers' best schedules, one per supplier. Each entry's `slateId` is bookable exactly like `primarySlate`'s. |
| `partial` | The best **PARTIAL** slate (fills fewer than the requested sessions). `null` unless the project has `suggestionConfig.allowPartialPackages` enabled. |
| `cadenceAlternatives` | **COMPLETE** N-session slates at a *different, supplier-feasible* cadence than the one you asked for. Sorted closest-first by `cadenceDistance` — unless you sent `sessionsPerWeek`, in which case closeness to that frequency target is the primary sort key, ahead of `cadenceDistance`. Always `[]` unless the request opted in — see [Cadence relaxation](#cadence-relaxation). |
| `requestedCadence` | The `rrule` this request asked for, echoed back so you can diff it against each slate's `cadenceRrule`. `null` when the request named no cadence. |

<Note>
Two schedules from the same supplier count as different options only when they run on
**different weekdays** or start **at least 30 minutes apart** — a supplier offering both 09:00
and 09:20 contributes one option, not two.
</Note>

### Status values

| `status` | Meaning |
| --- | --- |
| `OK` | A `COMPLETE` primary slate was found — every requested session filled by one supplier. |
| `ALTERNATIVE_CADENCE` | **A success, returned as `200`.** No slate at the *requested* cadence, but `cadenceAlternatives` holds one or more complete plans at a denser, supplier-feasible cadence. `primarySlate` is `null`; every alternative's `slateId` is bookable exactly like `primarySlate`'s. Only ever returned when the request opted in via `cadenceFlexibility` or `guaranteeSlate`. |
| `NO_COMPLETE_SLATE` | No complete single-supplier slate exists under the project's supplier policy. `alternates` may still be populated **under any `supplierPolicy`, including the default `SAME_SUPPLIER`** — here they're the same supplier's other PARTIAL schedules, so booking one still depends on `allowPartialPackages`. `partial` may also be usable (if `allowPartialPackages` is on) — check both before treating this as a dead end. |
| `NO_AVAILABILITY` | No availability at all for the request window — no supplier, complete or partial. |

<Warning>
The endpoint returns **`422`** only when `primarySlate`, `partial` **and**
`cadenceAlternatives` are *all* empty — nothing bookable at all. The `code`
is then the `status` (`NO_COMPLETE_SLATE` or `NO_AVAILABILITY`), not a `200`
with an empty body.

A non-empty `cadenceAlternatives` is bookable output, so it makes the
response a `200` (`ALTERNATIVE_CADENCE`) even with `primarySlate: null`.
**Don't branch on `primarySlate` alone** once you've opted into relaxation.
</Warning>

### Slate and slot fields

Each slate (`primarySlate`, entries in `alternates`, entries in
`cadenceAlternatives`, and `partial`) has the same shape:

| Field | Meaning |
| --- | --- |
| `slateId` | Book the whole plan with this — pass it as `slateId` to `POST .../package-bookings`. |
| `supplierId` | The single supplier this slate is built from. |
| `completeness` | `COMPLETE` or `PARTIAL`. |
| `sessionsRequested` / `sessionsFilled` | How many of the package's sessions this plan could fill, out of how many were requested. |
| `startTimeConsistencyPercent` | How consistent the session start times are (0–100). |
| `matchScore` | How well this slate matches the requested schedule preferences, `0`–`1` — the mean of the components in `matchComponents`. `1` with an empty `matchComponents` means no schedule preference was expressed, not a perfect match. See [How well a slate matches: `matchScore` and `matchComponents`](#how-well-a-slate-matches-matchscore-and-matchcomponents) below. |
| `matchComponents` | The per-criterion breakdown behind `matchScore` — carries only the criteria you actually supplied and that were scoreable for this slate. Present on every fresh availability response, empty when nothing was asked; absent entirely only on a slate resolved from a pre-existing booking rather than a fresh call — see below. |
| `cadenceSummary` | How often this plan actually runs, week by week, against the frequency you asked for: `requested`, `peak`, `average`, and a `byWeek` array. **Render `peak`, not `average`.** Present on every slate holding at least one session, on **every** request path — including the default `cadenceFlexibility: "NONE"` — and absent only for a slate with no sessions. See [How often a plan runs: `cadenceSummary`](#how-often-a-plan-runs-cadencesummary) below. |
| `matchNotes` | **Why** this slate departs from what you asked for — an array of coded reasons, each with structured evidence and no English. **Always present**; `[]` means nothing departed. Not gated on `matchScore`. See [Why a slate departs from your request: `matchNotes`](#why-a-slate-departs-from-your-request-matchnotes) below. |
| `advice` | An optional, **advisory** hint that starting later would help: `code` plus `earliestSustainedWeek`. It reports that supply exists from that week onward — not that a slate was built or would be bookable. Present only when one applies. See [A hint about starting later: `advice`](#a-hint-about-starting-later-advice) below. |
| `totalTravelTimeMins` | Summed travel time across the plan's sessions. |
| `slots[]` | The resolved sessions — see below. |

Slates additionally carry **cadence provenance** — a record of how the plan's
cadence relates to the one you asked for. These fields are absent unless the
request opted into [cadence relaxation](#cadence-relaxation):

| Field | Meaning |
| --- | --- |
| `cadenceRrule` | The recurrence rule this slate's sessions actually follow. **`null` for a direct fill** — that plan follows no recurrence rule at all. |
| `matchesRequestedCadence` | `true` when `cadenceRrule` is the `rrule` you asked for. |
| `cadenceRelaxation` | How the cadence was derived: `EXACT`, `INTERVAL_TIGHTENED` (same weekdays, run more often), `DAYS_ADDED` (every requested weekday kept, more added), `DAYS_SUBSTITUTED` (requested weekdays replaced with ones the supplier works), `ALL_WORKING_DAYS`, or `DIRECT_FILL`. |
| `cadenceDistance` | How far this cadence sits from the requested one — `0` is exact, lower is closer. `cadenceAlternatives` is sorted by it — unless the request sent `sessionsPerWeek`, in which case closeness to that frequency target sorts first, and `cadenceDistance` only breaks ties within it. |

<Note>
Cadence provenance is **provenance**: it records how the slate was generated.
It is not re-validated if a session is later rescheduled, so a booked plan can
drift from its own `cadenceRrule`.

[`cadenceSummary`](#how-often-a-plan-runs-cadencesummary) is deliberately
**not** in this table. It's measured from the slate's own sessions rather than
recorded from the request, so it isn't gated on relaxation and it isn't
provenance — it arrives on every path and is recomputed on every rebuild.
</Note>

Each entry in `slots[]`:

| Field | Meaning |
| --- | --- |
| `slotId` | Id of one session. Pass a subset of these as `slotIds` to cherry-pick instead of booking the whole slate. |
| `sessionIndex` | **1-based** position within the slate. |
| `supplierId`, `serviceId`, `offeringId` | Resolved identifiers for this session. |
| `bookingStartUtc`, `bookingEndUtc`, `bookingTz` | The resolved time. |
| `locationType`, `locationId`, `latitude`, `longitude`, `address` | The resolved location — for `TRAVEL_ZONE` slates the engine fills `locationId` (the supplier's travel-zone id) and stamps the request's `address` onto every slot. |
| `travelTimeMins` | Travel time to this session. |
| `capacity` | Session capacity. |
| `reservationStatus` | **Deprecated and inert** — always `FREE`. Holds are claims on *supplier time*, not on slot rows, so this field no longer tracks anything. Don't branch on it; see [Hold slots during checkout](/guides/hold-slots-for-checkout). |

<Tip>
**Off-by-one trap.** `sessionIndex` is **1-based** here in the slate's
`slots[]`, but **0-based** in the `created[]` array returned by
`POST .../package-bookings` (and `.../convert`). Don't compare them directly
without adjusting — see
[Create a package booking](/guides/create-a-package-booking).
</Tip>

### How well a slate matches: `matchScore` and `matchComponents`

`matchScore` is the arithmetic mean of the components present in
`matchComponents`, each itself a `0`–`1` ratio. There's no rounding.

Each component is a `0`–`1` ratio measured against what you asked for. Most
are measured over *this slate's own sessions*; `startDate` is measured
against the window instead, and `cadence` is binary rather than a ratio at
all:

| Component | Scored when | Meaning |
| --- | --- | --- |
| `startDate` | you sent `lookAheadStartDate` | how soon session one lands — `1` when it lands on the window's first day, lower the later it lands |
| `timeOfDay` | you sent `preferredTimes` | fraction of this slate's sessions that fall at a preferred time |
| `daysOfWeek` | you sent `daysOfWeek` | fraction of this slate's sessions that fall on a requested weekday |
| `sessionsPerWeek` | you sent `sessionsPerWeek` | fraction of the window's whole weeks in which this slate holds **at least** the target number of sessions — a ratio in `0`–`1`, never a count. For counts, read [`cadenceSummary`](#how-often-a-plan-runs-cadencesummary), which buckets weeks differently |
| `cadence` | you sent `rrule` **and** the slate follows a cadence | see below |

`excludeDates` is never a component — it's a hard filter, so it could only
ever score `1`, and including it would just dilute the mean. A component you
didn't ask about is simply left out of `matchComponents`, and the score is
the mean of whatever remains.

**The `cadence` component**, so you can predict its value:

- `1` when the slate runs at the `rrule` you requested.
- `1` also when the only departure was a weekday substitution you
  authorised — `cadenceRelaxation` of `DAYS_SUBSTITUTED` or
  `ALL_WORKING_DAYS`, with `allowWeekdaySubstitution: true` (the default) and
  **no** `daysOfWeek` sent. Naming your weekdays withdraws that
  authorisation, because it says the weekdays are the point.
- `0` when the cadence changed in a way you didn't authorise — including
  every change to how *often* sessions occur (`INTERVAL_TIGHTENED`,
  `DAYS_ADDED`). Allowing weekday substitution doesn't authorise a frequency
  change.
- **Absent, not `0`,** on a slate that follows no cadence at all: a
  `DIRECT_FILL` slate and a `PARTIAL` slate are both greedy fills that never
  consult your `rrule`, so the question is unanswerable rather than answered
  zero. Absent too when you sent no `rrule`.

A request that expresses no schedule preference at all gets `matchScore: 1`
with `matchComponents: {}`. Read `matchComponents`, not the score, to tell
"perfect match" from "nothing asked".

A fresh call to `/availability/package-slate` or `/availability/package-options`
always carries `matchComponents`, even when it's empty. The key is absent
entirely only on a slate resolved from a booking made before this shipped —
the book-by-`slateId`, `409`-stale-rebuild, and reschedule paths read an
existing row rather than running a fresh match, so that row's `matchScore: 1`
comes back with no `matchComponents` at all. Treat a missing key as "no data
recorded", a third case alongside "perfect match" and "nothing asked".

<Warning>
Results already arrive ranked. `primarySlate` is the best-matching
**COMPLETE** slate and `alternates` follow it in descending order;
**completeness always outranks `matchScore`**, so a COMPLETE slate is never
placed below a PARTIAL one that scored higher. (`cadenceAlternatives` is
ordered separately, closest-cadence first.)

**Don't re-sort the slates you receive by `matchScore`.** The order carries a
preference the number can't. `matchComponents.sessionsPerWeek` scores a week
holding **at least** the target, so against a target of `2` a slate
delivering three sessions a week scores exactly the same as one delivering
two — only the order distinguishes them. Re-sorting silently discards "two,
not three".
</Warning>

### How often a plan runs: `cadenceSummary`

`cadenceSummary` answers the one question a booking UI has to render — "how
often is this plan?" — and it answers it week by week rather than as a single
rate. It's on every slate holding at least one session, on **every** request
path, including the default `cadenceFlexibility: "NONE"`. It's absent only for
a slate with no sessions at all, which has no cadence to describe.

```json
{
  "cadenceSummary": {
    "requested": 4,
    "peak": 4,
    "average": 2.25,
    "byWeek": [
      { "weekStart": "2026-09-07", "sessions": 1 },
      { "weekStart": "2026-09-14", "sessions": 0 },
      { "weekStart": "2026-09-21", "sessions": 4 },
      { "weekStart": "2026-09-28", "sessions": 4 }
    ]
  }
}
```

| Field | Meaning |
| --- | --- |
| `requested` | The frequency you asked for, in sessions per week — your `sessionsPerWeek` target when you sent one, otherwise the number of weekdays your own `rrule` named (`FREQ=WEEKLY;BYDAY=MO,TU,WE,TH` is `4`). `null` when you expressed no frequency at all, and `null` too when the rule wasn't yours to count: a non-weekly `FREQ`, an `INTERVAL` other than `1`, a weekly rule naming no weekdays, or a cadence this API synthesised on your behalf. Reporting a frequency you never asked for is worse than reporting none. |
| `peak` | The most sessions this plan holds in any single week. **This is the number to render.** |
| `average` | Sessions divided by the number of entries in `byWeek`, to two decimal places. For capacity and reporting — not for client-facing copy. |
| `byWeek` | Every **Monday-anchored** week from the first session's week through the last session's: ascending, contiguous, and including weeks holding `0` sessions. Never empty. |

**Render `peak`, not `average`.** The nine sessions above run 1 / 0 / 4 / 4 —
the supplier has a week off in the middle of the plan. Those four weeks
average `2.25`, and not one week in the plan runs at `2.25`. An average is the
one number that describes none of the weeks, which is how a nine-session plan
that plainly runs at four a week wherever it runs ends up rendered as
"1.67×/week". `peak` is the honest answer.

`average` is still worth having, because it's verifiable: it is exactly the
sum of `byWeek`'s `sessions` divided by `byWeek`'s length, so you can check it
against the array in the same response. The weeks it divides by span the
**plan** — the first session's week through the last session's, gap weeks
included — never your whole look-ahead window, so asking for a wide window
doesn't dilute it.

The zero week is the most useful entry in `byWeek`. It's a week inside the
plan where the supplier had nothing, not a hole in this data — and it's what
lets you explain an uneven plan to a client ("week three is off, then you're
back to four a week") instead of apologising for one.

<Warning>
**`cadenceSummary` and `matchComponents.sessionsPerWeek` count weeks
differently, on purpose.** They are not two views of the same number:

- `cadenceSummary.byWeek` buckets **Monday-anchored calendar weeks**, so every
  `weekStart` is a real Monday and the buckets agree with how the
  `maxSessionsPerWeek` cap counts.
- `matchComponents.sessionsPerWeek` — the `0`–`1` ratio above, not a count —
  buckets **consecutive 7-day blocks from your window's start**, so it stays
  comparable with `availabilityMatch` on
  [`POST /availability/suppliers`](/guides/search-suppliers-by-availability).

They can therefore disagree, and both are right. `peak: 4` against a target of
`4` while that component reads below `1` is exactly what a supplier's mid-plan
break looks like: every week the plan runs, it runs at four — but the whole
weeks of your window don't all hold four. Don't file that as a bug.
</Warning>

<Note>
`cadenceSummary` behaves differently from its neighbours on a reschedule.
`matchScore` and `matchComponents` are provenance and are never re-derived,
but `peak`, `average` and `byWeek` are **recomputed from the slate's current
sessions** every time the slate is rebuilt; only `requested` is snapshotted
from the original request. So a slate can come back from a reschedule with an
unchanged `matchScore` and a *changed* `cadenceSummary`.
</Note>

## Why a slate departs from your request: `matchNotes`

`matchScore` says *how well* a slate matches. `matchComponents` says *which*
criterion missed. `matchNotes` says **why** — one entry per reason, each a
machine-readable code carrying the evidence behind it.

```json
{
  "matchNotes": [
    {
      "code": "WEEK_SUPPLY_INSUFFICIENT",
      "component": "sessionsPerWeek",
      "weekStart": "2026-09-14",
      "evidence": {
        "sessionsPlaced": 0,
        "sessionsTargeted": 4,
        "openingsInPool": 0
      }
    }
  ]
}
```

That single note is the 1 / 0 / 4 / 4 plan from
[`cadenceSummary`](#how-often-a-plan-runs-cadencesummary) above, explained: the
`0` week is `2026-09-14`, you asked for four sessions in it, and the plan placed
none. `openingsInPool: 0` is the part that tells you why — the supplier's
candidate pool held nothing placeable that week, so waiting is the move and
`advice` names the week to wait for.

| Field | Meaning |
| --- | --- |
| `code` | Which reason this is — one of the nine below. The discriminator: each code carries its own `evidence` shape, so your generated types tell you exactly which fields are present rather than handing you a bag of optionals. |
| `component` | The `matchComponents` criterion this note explains — `sessionsPerWeek`, `cadence`, `timeOfDay` or `startDate`. Group notes by it to caption a component directly. Present on eight of the nine codes; `PACKAGE_UNDERFILLED` has **no** `component`, because plan size isn't a scored criterion. A pointer, not a join key: the week-level codes bucket Monday-anchored calendar weeks while `matchComponents.sessionsPerWeek` buckets 7-day blocks from your window's start, so a note can name a short week for a criterion that component scores as met, and the reverse. |
| `weekStart` | The Monday (`YYYY-MM-DD`, local) of the week this note is about. Only on the five week-level codes, and bucketed exactly like `cadenceSummary.byWeek`, so a note joins to a `byWeek` entry on this key. |
| `evidence` | The numbers behind the code — counts, weekdays, dates. Its shape is fixed per code. |

<Note>
**There is deliberately no `message`.** No English ships in a note, so you keep
your own voice and can localise: write the copy, and use `evidence` to fill in
the week, the weekday or the count. A prewritten sentence would have to be
translated by every integrator anyway, and it would tempt you to render our
wording to a client instead of yours.
</Note>

`matchNotes` is **always present**. Nothing departed from your request means
`[]`, not a missing key, so you can read `.length` without a null check. It is
**not gated on `matchScore`** either: a `DIRECT_FILL` slate and a `PARTIAL`
slate can both score `1` and still carry notes, and those are exactly the
slates worth captioning.

Weekday numbers anywhere in `evidence` are **`0` = Sunday … `6` = Saturday** —
the same numbering request-level `daysOfWeek` uses.

**Group the week-level notes by `code` before you render them.** One note is
emitted per short week, so a Monday-only supplier against a target of two emits
`WEEK_SUPPLY_INSUFFICIENT` on *every* week of the plan — a caption per note gives
you four near-identical sentences. Collapse each group into one line that names
the weeks: "four weeks come back short — 6, 13, 20 and 27 July".

<Note>
`matchNotes` and `advice` are **provenance**, like `cadenceRrule`: they record
what was true when the slate was generated. Rescheduling a session recomputes
`startTimeConsistencyPercent`, `totalTravelTimeMins` and `cadenceSummary`, but
not these — so a rescheduled slate can come back carrying a note its current
sessions no longer justify. Slates built before this shipped read back with
`matchNotes: []` and no `advice`.
</Note>

### The nine codes

| Code | `component` | Emitted when | What it licenses you to say |
| --- | --- | --- | --- |
| `SUPPLIER_UNAVAILABLE_WEEK` | `sessionsPerWeek` | The supplier works **none** of the weekdays that could have served this week — `evidence.supplierWorkdays` is `[]`. **Not currently emitted by the live engine** — see the section below before you build for it. | "This supplier doesn't work any of the days that week needed — the sessions moved to the weeks either side." Check `advice` for the earliest week supply resumes. |
| `WEEK_EXCLUDED_BY_FILTERS` | `sessionsPerWeek` | Your own `daysOfWeek` or `excludeDates` cut this week's candidate days below your target, and the supplier's working **pattern** covers enough days in the week to have met it without your filter. `evidence.filter` names which one. Like `supplierWorkdays` everywhere else, that is a pattern fact, not a check of this calendar week — a supplier already booked solid across it reports this code too. | "Your day preferences are what's limiting this week — allowing one more weekday is the thing most likely to fill it." Say *likely*: loosening the filter is the best move the evidence supports, not a guarantee. |
| `WEEK_SUPPLY_INSUFFICIENT` | `sessionsPerWeek` | The week is short and none of the more specific reasons could be **established**. This is the residual code: the supplier's working *pattern* is not empty (which is what rules out `SUPPLIER_UNAVAILABLE_WEEK` — a pattern fact, not a check of this calendar week), and the shortfall could not be attributed to one of your filters or to a cap you sent — which is not the same as those playing no part. | Don't lead with "the supplier didn't have enough open days" — compare `sessionsPlaced` and `sessionsTargeted` against `openingsInPool` first, and see the note below for the two cases where a filter or a cap *was* involved. |
| `WEEK_CAPPED` | `sessionsPerWeek` | The week held at least `sessionsTargeted` placeable days, and a cap **you** sent puts a ceiling on the week below your target — so the target was unreachable there whatever the supplier had free. `evidence.cap` is `maxSessionsPerWeek` or `minGapDays`, with its `capValue`. It fires on the ceiling *existing*, not on the plan having filled up to it. | "That week is capped by your own settings — raise the cap for a denser week." Raising it is **necessary**; whether it's **sufficient** this note can't say. If `sessionsPlaced` sits below the ceiling the cap implies, all you know is that the plan didn't fill the week even to the ceiling — don't read a second cause into it. |
| `SESSIONS_EXHAUSTED` | `sessionsPerWeek` | The week is short only because the package ran out of sessions. | Nothing apologetic — see the dedicated section below. |
| `CADENCE_RELAXED` | `cadence` | The slate doesn't run at the `rrule` you sent. `evidence.cadenceRelaxation` says how the cadence was derived; `requestedDays` and `actualDays` let you show the swap. | "We moved your Tuesdays to Thursdays" / "this plan runs weekly rather than fortnightly." |
| `SESSIONS_OUTSIDE_PREFERRED_TIMES` | `timeOfDay` | Some sessions fall outside every `preferredTimes` window you sent. `evidence.sessionIndexes` is **1-based** and matches `sessionIndex` on the slots; `localTimes` is aligned to it. **Both arrays can be empty** — when no session lands inside your requested window at all, the criterion definitely missed but there is no in-window session to name. | "Sessions 3 and 7 are at 08:00, outside your afternoon preference." Handle the empty case: caption it "outside your preferred times" with no session list, not as an error. |
| `FIRST_SESSION_LATE` | `startDate` | The plan's first session is `evidence.dayOffset` whole days after your window start — always at least one. That offset is the fact; whether the plan started later than it *had* to is a separate question. | Branch on `evidence.earlierSupplyExisted`. `true`: the supplier *was* free earlier and the cadence couldn't use those days, so "we could have started on the 7th — loosening the cadence is the fix." `false`: no earlier opening existed in your window, so "the earliest this supplier opens is the 14th" — nothing was given up, and copy implying otherwise is wrong. |
| `PACKAGE_UNDERFILLED` | *(none)* | Fewer sessions than the package holds credits for. | "We could only plan 6 of the 8 sessions." `completeness` says `PARTIAL` too. |

<Note>
**`WEEK_SUPPLY_INSUFFICIENT` is the residual code, not a finding about supply.**
Reaching it means only that the supplier's working *pattern* is not empty — which
is what rules out `SUPPLIER_UNAVAILABLE_WEEK`, and is a fact about the weekdays
they work at all rather than a check of this calendar week — and that the
shortfall could not be *attributed* to one of your filters or to a cap. It does
not mean neither was involved. Two cases land here with one of them genuinely in
play:

- a filter removed a candidate day from a week the supplier's own pattern days
  could never have met anyway (attribution is withheld because loosening the
  filter provably could not have reached your target);
- a cap applied to a week whose openings were already below your target
  (`WEEK_CAPPED` is reserved for weeks that had enough openings to make the cap
  the thing to raise).

So read the evidence rather than assuming supply was the constraint. When
`openingsInPool` is **below** `sessionsTargeted`, the placeable days genuinely
weren't there. When it's **at or above** the target, the days were there and
something else was in the way — look for `CADENCE_RELAXED` on the same slate,
which reports a cadence that couldn't use them and is the better thing to tell a
client. That pointer doesn't always land: `CADENCE_RELAXED` is only emitted when
the cadence criterion scored below `1`, and an **authorised weekday
substitution** scores a perfect cadence — so a days-were-there week can carry no
cadence note at all. When it doesn't, say the week came back short and stop
there rather than naming a cause.

`openingsInPool` counts **placeable days**, not slots: a plan places at most one
session per local date, so a day offering five start times counts once. That's
what makes it directly comparable to `sessionsTargeted`.
</Note>

### "Wait a week" or "loosen your days"

A week that comes back short of your target has two very different explanations,
and they are **opposite calls to action**. One means the constraint is the
supplier's and yours can't fix it; the other means the constraint is yours and
one click fixes it. Tell a client the wrong one and you've either sent them away
from a supplier who was available, or had them wait out a week that was never
blocked. Getting this pair right is the reason `matchNotes` exists.

<Warning>
**`SUPPLIER_UNAVAILABLE_WEEK` is not currently emitted by the live engine.** It
is part of the published contract and you should keep it in your `switch` — but
it fires only when a supplier works no weekday at all, and a supplier like that
produces no availability, so no candidate, so no slate for the note to attach
to. Don't build your "waiting helps" copy on it: nothing will reach it today.

**The supplier-break case reaches you as `WEEK_SUPPLY_INSUFFICIENT` with
`openingsInPool: 0`.** That is the combination to key your "waiting may help"
copy on, and `advice.earliestSustainedWeek` is the week to name.
</Warning>

So the pair you actually branch on is `WEEK_SUPPLY_INSUFFICIENT` with an empty
pool against `WEEK_EXCLUDED_BY_FILTERS`.

**The supplier had nothing open.** No `daysOfWeek` filter, a target of two a
week, a Monday-to-Friday supplier whose diary is full across the week:

```json
{
  "code": "WEEK_SUPPLY_INSUFFICIENT",
  "component": "sessionsPerWeek",
  "weekStart": "2026-07-06",
  "evidence": {
    "sessionsPlaced": 0,
    "sessionsTargeted": 2,
    "openingsInPool": 0
  }
}
```

`openingsInPool: 0` with no filter of yours named anywhere is as close as the
API gets to "there was nothing to book that week". Waiting is the honest thing
to say, and `advice` is where you look next.

**Your own filter cut the week down.** `daysOfWeek: [1]` (Mondays only), the
same target of two a week, a Monday-to-Friday supplier with one open Monday in
the week:

```json
{
  "code": "WEEK_EXCLUDED_BY_FILTERS",
  "component": "sessionsPerWeek",
  "weekStart": "2026-07-06",
  "evidence": {
    "sessionsPlaced": 1,
    "sessionsTargeted": 2,
    "filter": "daysOfWeek",
    "supplierWorkdays": [1, 2, 3, 4, 5],
    "requestedDays": [1]
  }
}
```

`supplierWorkdays: [1, 2, 3, 4, 5]` against `requestedDays: [1]` is the whole
argument: one Monday a week can never make two sessions a week, and there are
four other weekdays this supplier works. **Loosening `daysOfWeek` is the move
here, and waiting is not.** `supplierWorkdays` is the pre-filter fact that makes
this call possible at all — the candidate pool alone can't, because your
`daysOfWeek` and `excludeDates` were already applied to it, so "no openings this
week" looks identical whether the supplier had nothing or you removed
everything.

<Warning>
**`supplierWorkdays` is a fact about the supplier's working *pattern*, not a
check of that particular calendar week** — and this is true wherever it appears,
on `WEEK_EXCLUDED_BY_FILTERS` as much as on `SUPPLIER_UNAVAILABLE_WEEK`. The API
answers "which weekdays does this supplier work at all", never "was this
specific week covered" — answering the second would mean re-expanding every
recurrence rule on the booking hot path.

Two consequences worth designing for. A supplier who works Mondays but happens
to be booked out on *this* week's Monday reports `WEEK_SUPPLY_INSUFFICIENT`, not
`SUPPLIER_UNAVAILABLE_WEEK`. And a Monday-to-Friday supplier who is booked solid
across the week still reports `WEEK_EXCLUDED_BY_FILTERS` if your `daysOfWeek`
narrowed it — the pattern days were there even though the openings weren't. So
treat "loosen your filter" as the **most likely** fix rather than a guaranteed
one; it is the best move the evidence supports, but the API has not checked that
those extra weekdays were free.

`WEEK_EXCLUDED_BY_FILTERS` is still only emitted when relaxing your filter could
have helped: a week the supplier's own pattern could never have met is reported
as `WEEK_SUPPLY_INSUFFICIENT` instead, and is not your filter's fault. The one
exception is a `daysOfWeek` naming no day this supplier works at all, which
leaves zero candidate days whatever your target.
</Warning>

### `SESSIONS_EXHAUSTED` means nothing went wrong

Nine sessions at four a week leaves the last week holding one. That week *is*
short of your target, and it is short for the most ordinary reason there is:
the package ran out of credits. Nothing failed.

```json
{
  "code": "SESSIONS_EXHAUSTED",
  "component": "sessionsPerWeek",
  "weekStart": "2026-07-20",
  "evidence": {
    "sessionsRequested": 3,
    "sessionsPlacedBefore": 2
  }
}
```

`sessionsPlacedBefore` is how many of the package's sessions the earlier weeks
already used — two of three here, so the final week could only ever hold one,
whatever the supplier's diary looked like.

<Warning>
**Don't apologise for `SESSIONS_EXHAUSTED`, and don't surface it as a problem.**
It outranks every supply code: when it's emitted for a week, no
`SUPPLIER_UNAVAILABLE_WEEK`, `WEEK_EXCLUDED_BY_FILTERS`,
`WEEK_SUPPLY_INSUFFICIENT` or `WEEK_CAPPED` is emitted for that same week. It
exists precisely so a correctly-filled plan doesn't read as a supplier failure —
without it, the tail week of every package looks like something went wrong.
Render it as a plain fact if you render it at all ("the last week runs once —
that's the eighth and final session"), or drop it.
</Warning>

### A hint about starting later: `advice`

<Warning>
**`advice` is advisory only.** It reports that the supplier has enough open
**supply** from a given week onward to sustain the frequency you asked for. It
does **not** mean a slate was built for that week, or that one would be
bookable — holds, capacity, travel time and the cadence rules all still apply.
Re-request with a later `lookAheadStartDate` to find out for real. Don't
promise a client a schedule nobody has validated.
</Warning>

With that stated, the shape is small:

```json
{
  "advice": {
    "code": "LATER_START_IMPROVES_CADENCE",
    "earliestSustainedWeek": "2026-09-21"
  }
}
```

| Field | Meaning |
| --- | --- |
| `code` | Always `LATER_START_IMPROVES_CADENCE` today. Branch on it anyway — it's an enum so more hints can be added without a breaking change. |
| `earliestSustainedWeek` | The earliest Monday (`YYYY-MM-DD`, local) from which supply alone could sustain your requested frequency. |

`advice` is **optional** — present only when a later start would actually help.
It's absent when you expressed no frequency target, when no week fell short, and
when no week in your window sustains the target from that point on. Absent is
the honest answer in all three cases; the field never points at a week that
doesn't hold up.

"Sustain" is strict: every remaining whole week in your window, from
`earliestSustainedWeek` to the end of the window, holds at least your target in
open days — not just the named week itself. A week that meets the target and
then dips below it a fortnight later is never returned, because you'd hang a
client promise on it.

Read it alongside a `WEEK_SUPPLY_INSUFFICIENT` note carrying
`openingsInPool: 0`: that pairing says "waiting is the move", and this field
names the week to wait for. In the 1 / 0 / 4 / 4 plan above, `2026-09-14` is the
empty week and `earliestSustainedWeek` is `2026-09-21` — the Monday supply
resumes and stays resumed. `earliestSustainedWeek` is always **strictly later**
than the first week the notes reported as short, so it never names a week the
same response has already called short.

## Cadence rules: `rrule` and `lookAheadStartDate`

`package-slate` derives its whole session plan from two request-shape
guarded fields. Both are enforced at validation time (a `400` before the
engine ever runs), not just documented convention.

### `rrule` needs a bounded, positive `COUNT`

```
✅ FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;COUNT=8
❌ FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR
```

An unbounded `rrule` almost never returns anything bookable — the engine
needs a specific number of occurrences to try to fill, not an open-ended
pattern. Omitting `COUNT` (or giving `COUNT=0`) fails validation:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "rrule: 'rrule' must include a bounded COUNT (e.g. 'FREQ=WEEKLY;BYDAY=MO;COUNT=8')",
  "statusCode": 400,
  "requestId": "4b8e2f1a-7c9d-4a56-b3e0-8d5f1c9a4e67"
}
```

<Note>
The `message` is prefixed with the offending field name (`rrule: …`) — the
validation layer prepends the field path to every schema error.
</Note>

### `lookAheadStartDate` needs a numeric offset, not `Z`

```
✅ 2026-07-09T00:00:00-04:00
❌ 2026-07-09T00:00:00Z
```

The recurring builder derives the request's UTC offset from the **last six
characters** of `lookAheadStartDate`, so a `Z` suffix produces a garbage
offset and silently wrong results — the API rejects it outright instead:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "lookAheadStartDate: 'lookAheadStartDate' must carry a numeric timezone offset (e.g. '2026-07-01T00:00:00-04:00'), not a 'Z' suffix",
  "statusCode": 400,
  "requestId": "a6d3f9e8-2b5c-4d17-9e04-6a8c3f1b5d92"
}
```

### The 120-day look-ahead ceiling

You don't have to compute the look-ahead window yourself — by default it's
**derived from your cadence and the package's `creditCount`**, so the engine
searches exactly as far ahead as it needs to fit every session. That
derived window is capped at **120 days**.

That ceiling is wide enough for the ordinary weekly product. A weekly
10-session package (`FREQ=WEEKLY;BYDAY=MO;COUNT=10`) spans about 70 days —
comfortably inside the window — so it plans and books normally. Weekly
12-packs (~84 days) and biweekly 5-packs (~70 days) fit too.

What happens when the cadence is too sparse to fit all of a package's
sessions within 120 days **depends on whether you asked for cadence
flexibility**. The two behaviours are genuinely different code paths:

| `cadenceFlexibility` | Behaviour when the derived window exceeds 120 days |
| --- | --- |
| `NONE` (the default) | **Fails fast with a `422` before running the engine at all**, naming the exact window it would have needed. Nothing is silently truncated. |
| `FALLBACK` / `ALWAYS` (or `guaranteeSlate: true`) | **Clamps the window to 120 days and runs the engine anyway.** No early return. |

The clamp is not a loosened guardrail — it's the whole point of relaxation.
A denser cadence needs a *shorter* window, so the over-window case is exactly
the one the [relaxation ladder](#cadence-relaxation)
can answer: Monday-only `COUNT=20` needs 134 days ✗, but the same 20 sessions
twice a week need only 70 ✓. Returning early would short-circuit the feature
before it ever got to try.

For example, a package with `creditCount: 20` requested with a Monday-only
cadence (`FREQ=WEEKLY;BYDAY=MO;COUNT=20`) needs about 20 weeks (134 days
including the inclusive end boundary) to fit all 20 sessions — over the cap.
On the default `NONE` path nothing is bookable, so this comes back as a `422`
in the standard [error envelope](/concepts/errors) (the `reason` becomes
`message` and the `status` becomes `code`), **not** a `200` with a slate body:

```json
{
  "code": "NO_COMPLETE_SLATE",
  "message": "package cadence requires 134-day availability window for 20 sessions, which exceeds the 120-day maximum",
  "statusCode": 422,
  "requestId": "1f5b8d3a-4e9c-4a72-b6d1-3f0a8c5e2b46"
}
```

Send the *same* request with `cadenceFlexibility: "FALLBACK"` and you get a
`200` instead: the window clamps to 120 days, the engine runs, and any
complete denser plan the supplier can actually fill comes back in
`cadenceAlternatives` with `status: "ALTERNATIVE_CADENCE"`. If even the
relaxed cadences fail, it's a `422` again — the clamp buys the engine a
chance to answer, it doesn't manufacture availability.

Compare that to the working example from
[Create a package booking](/guides/create-a-package-booking): an 8-session
package with `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;COUNT=8` fits 8 sessions into
under two weeks (five eligible weekdays per week), well inside the cap.

<Tip>
If you need a window wider than the derived default, pass `lookAheadDays` or
`endDate` explicitly. **Doing so skips the derivation entirely — you own the
window.** Neither the 120-day cap nor the relaxation padding is applied to a
window you sized yourself: the 120 is a ceiling on the window the API
*derives* from your cadence, not a ceiling the engine enforces on a window you
state outright. So an explicit `lookAheadDays: 200` really does search 200
days.

The trade is that nothing sanity-checks it for you. Too small and the cadence
can't fit; too large and you pay for pool the engine has to build. See the
warning below for what an explicit window costs a relaxation request
specifically.
</Tip>

<Warning>
**An explicit `lookAheadDays` or `endDate` also opts you out of the padding
that cadence relaxation relies on.** When the window is derived, a relaxation
request widens it by a few days so a weekday *substitution* — which can need a
slightly longer span than the cadence you asked for — has room to land. Size
the window yourself and that padding is gone, so a substituted cadence needing
a handful more days is silently dropped from `cadenceAlternatives`. If you're
combining `cadenceFlexibility` with an explicit window, budget a week of
headroom, or let the derivation do it for you.
</Warning>

## Cadence relaxation

A supplier who works every weekday still can't give you eight *Fridays* if
their schedule only runs four weeks. Historically that returned an empty
`422` and left you with nothing to show — the single biggest complaint
against the booking engine.

Now you can ask the engine to answer with a **denser, supplier-feasible
cadence** instead: complete N-session plans that fit the supplier's real
availability but don't follow the `rrule` you asked for. They arrive in
`cadenceAlternatives`, each with a directly bookable `slateId`.

<Warning>
**This is strictly opt-in, and the opt-in is absolute.** A request that sets
neither `cadenceFlexibility` nor `guaranteeSlate` behaves *exactly* as it did
before this feature existed — same slates, same statuses, same `422`s.
`cadenceFlexibility` defaults to `NONE`, `cadenceAlternatives` comes back
empty, and `ALTERNATIVE_CADENCE` is unreachable. **You cannot be broken by
this change without asking for it.**
</Warning>

### Request fields

All seven are optional, and all seven exist on both `/availability/package-slate`
and `/availability/package-options`:

| Field | Type | Default | What it does |
| --- | --- | --- | --- |
| `cadenceFlexibility` | `"NONE"` \| `"FALLBACK"` \| `"ALWAYS"` | `"NONE"` | The master switch. `NONE` is today's behavior. `FALLBACK` returns `cadenceAlternatives` **only when the requested cadence yields nothing**. `ALWAYS` returns them alongside a successful `primarySlate` too, so you can offer "…or twice a week". |
| `guaranteeSlate` | `boolean` | `false` | Try harder before giving up — adds the direct-fill floor below. Implies `cadenceFlexibility: "FALLBACK"`, so setting this alone is enough. |
| `maxCadenceAlternatives` | integer `0`–`10` | `3` | Cap on entries in `cadenceAlternatives`. Ignored when flexibility is `NONE`. |
| `allowWeekdaySubstitution` | `boolean` | `true` | Whether a relaxed cadence may **drop** a weekday you asked for. Set `false` when the requested day is non-negotiable (the client is only home on Fridays) — the engine may then only *add* days, never swap them. |
| `minGapDays` | integer `0`–`90` | *(none)* | Minimum whole days between consecutive sessions **in the direct fill** (`guaranteeSlate`) only — not applied to any cadence-ladder rung in `cadenceAlternatives`. Use it to stop a direct fill from stacking sessions on back-to-back days. |
| `maxSessionsPerWeek` | integer `1`–`14` | *(none)* | Cap on sessions per **Monday-anchored** calendar week **in the direct fill** (`guaranteeSlate`) only — no rung in `cadenceAlternatives` is filtered by it, so a `FALLBACK`/`ALWAYS` response can still return a denser week than this cap. |
| `sessionsPerWeek` | integer `1`–`14` | *(none)* | A frequency **target**, independent of which weekdays — "twice a week". Distinct from `maxSessionsPerWeek`, which is a **cap**. Steers which cadences are offered and in what order; also stands in as the direct-fill cap when no `maxSessionsPerWeek` was given. |

Two further optional fields — `daysOfWeek` and `excludeDates` — also exist on
both endpoints. They aren't relaxation controls; they constrain which calendar
days *any* plan may use, relaxed or not. See
[Schedule preferences](#schedule-preferences-daysofweek-and-excludedates).

### What comes back

When relaxation produces something and the requested cadence didn't, the
response is a **`200`** with `status: "ALTERNATIVE_CADENCE"`, `primarySlate:
null`, and a populated `cadenceAlternatives` sorted closest-first by
`cadenceDistance`. Every entry is a normal slate: book it by `slateId`, hold
it by `slateId`, transcribe its `slots[]` — all three paths in this guide
work identically on an alternative.

### Worked example

A supplier works **Mon–Fri, 09:00–17:00**, `America/Toronto`, on a schedule
that runs **2026-07-06 → 2026-08-03** — about four weeks. The client wants an
**8-session package** on Fridays. Eight Fridays would run to late August;
the schedule ends after the fourth. So the requested cadence is unfillable
even though the supplier is demonstrably available.

Send this body to `POST /availability/package-slate`:

```json
{
  "packageId": "pkg_01kv7n10k0fnptwk81wkm59vj7",
  "locationId": "loc_01kv60qgs4e4nbjhzradnqtj0h",
  "timezone": "America/Toronto",
  "lookAheadStartDate": "2026-07-06T00:00:00-04:00",
  "rrule": "FREQ=WEEKLY;BYDAY=FR;COUNT=8",
  "cadenceFlexibility": "FALLBACK"
}
```

With `cadenceFlexibility` omitted (or `"NONE"`), that request is a **`422`
`NO_COMPLETE_SLATE`** — unchanged, and still the default. With `"FALLBACK"`,
the same request returns a **`200`**, and the response carries a complete
eight-session plan on **Mondays and Fridays**:

```json
{
  "status": "ALTERNATIVE_CADENCE",
  "reason": "no complete slate at the requested cadence; returning alternative cadences",
  "requestedCadence": "FREQ=WEEKLY;BYDAY=FR;COUNT=8",
  "primarySlate": null,
  "alternates": [],
  "partial": null,
  "cadenceAlternatives": [
    {
      "slateId": "slate_01kx16ejsqffc9rbgdcc591w2p",
      "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
      "completeness": "COMPLETE",
      "sessionsRequested": 8,
      "sessionsFilled": 8,
      "matchScore": 0.5,
      "matchComponents": { "startDate": 1, "cadence": 0 },
      "cadenceRrule": "FREQ=WEEKLY;BYDAY=MO,FR;COUNT=8",
      "matchesRequestedCadence": false,
      "cadenceRelaxation": "DAYS_ADDED",
      "cadenceDistance": 2,
      "cadenceSummary": {
        "requested": 1,
        "peak": 2,
        "average": 2,
        "byWeek": [
          { "weekStart": "2026-07-06", "sessions": 2 },
          { "weekStart": "2026-07-13", "sessions": 2 },
          { "weekStart": "2026-07-20", "sessions": 2 },
          { "weekStart": "2026-07-27", "sessions": 2 }
        ]
      },
      "slots": []
    }
  ]
}
```

(Abridged: `suggestionRequestId`, `resolvableUntil` and the remaining two
alternatives are omitted, and `slots[]` is collapsed as elsewhere on this
page.) `matchScore` is `0.5`, not `1`: `DAYS_ADDED` is a frequency change the
request didn't authorise, so `cadence` scores `0` and drags the mean down
from the `startDate` component's `1`.

The eight sessions land on **Jul 6, 10, 13, 17, 20, 24, 27 and 31** — all
inside the supplier's schedule, where eight Fridays would have needed until
late August. `cadenceRelaxation` is `DAYS_ADDED` because Friday was *kept*
and one weekday was added; `cadenceDistance: 2` ranks it as the closest
answer available.

`cadenceSummary` reads that same plan back as a cadence: `requested: 1`,
because the `rrule` you sent named one weekday, against a `peak` of `2` — the
number to put in front of a client. Here the plan runs at exactly two a week
in all four of its weeks, so `average` matches `peak`; the two only part
company when a week comes up short.

<Note>
Monday is chosen, not Wednesday or Thursday, because when the engine adds a
weekday it **maximises the spacing between sessions**. `{MO, FR}` leaves gaps
of 4 and 3 days; `{TH, FR}` would leave 1 and 6. Sessions spread evenly
across the week beat sessions bunched against the day you asked for.
</Note>

Here the default `maxCadenceAlternatives: 3` means three plans come back —
`MO,FR` first, then progressively denser ones. Render them as a choice
("we can't do 8 Fridays, but we can do 8 sessions on Mondays and Fridays")
rather than picking one silently.

### Asking for a frequency: "twice a week, any day"

A frequency picker collects "twice a week" with no weekday preference.
`rrule` can't express that on its own — it names specific weekdays — and
`daysOfWeek` is a hard filter, so naming days there would rule every other
day out.

Send `sessionsPerWeek` alongside a starting-point `rrule` instead. Here's a
complete body for `POST /availability/package-slate`: `rrule` is
**required** on this endpoint, so the two weekdays in it are a starting
point, not a constraint — `sessionsPerWeek` states the real target, and
`allowWeekdaySubstitution` (default `true`) lets the engine move the days to
hit it:

```json
{
  "packageId": "pkg_01kvr4cgb3esg8hxx32kwhre7g",
  "locationId": "loc_01kv60qgs4e4nbjhzradnqtj0h",
  "timezone": "America/Toronto",
  "lookAheadStartDate": "2026-07-06T00:00:00-04:00",
  "rrule": "FREQ=WEEKLY;BYDAY=MO,TH;COUNT=8",
  "sessionsPerWeek": 2,
  "cadenceFlexibility": "ALWAYS"
}
```

**Omit `daysOfWeek` entirely.** Sending it would make `MO,TH` a hard filter
and, on top of that, withdraw the `cadence` component's substitution
exemption (see [above](#how-well-a-slate-matches-matchscore-and-matchcomponents)).
On `/availability/package-options`, `rrule` is optional; omit it there and
the cadence is synthesised per package from its credit count, with
`sessionsPerWeek` still steering.

`sessionsPerWeek` is always *scored* — `matchComponents.sessionsPerWeek`
comes back on any slate — but it only *steers which slates get built* when
cadence relaxation actually runs. That means `cadenceFlexibility: "ALWAYS"`,
or `"FALLBACK"` once the requested cadence yields nothing, or
`guaranteeSlate: true` (which promotes `NONE` to `FALLBACK`). On the default
`"NONE"`, the `rrule` fixes the schedule completely, and the target is
scored but changes nothing about which slates come back.

Where to read the answer — and the trap that pairs with the point above:

- With `"ALWAYS"` and a fillable requested cadence: `status: "OK"`, the
  answer is `primarySlate`, and `cadenceAlternatives` carries the denser
  options alongside it.
- When the requested cadence can't be met but a relaxed one can:
  **`status: "ALTERNATIVE_CADENCE"`, `primarySlate` is `null`, and the
  answer is `cadenceAlternatives[0]`** — already ordered closest-first, with
  the frequency target ranked ahead of raw cadence distance. This is a
  `200`, not a failure. **A client that reads only `primarySlate` concludes
  there's no availability when a bookable plan is sitting right there** —
  see the warning under [Status values](#status-values), which already
  makes the "don't branch on `primarySlate` alone" point.
- Take `cadenceAlternatives[0]` rather than re-sorting by `matchScore` — see
  the [warning above](#how-well-a-slate-matches-matchscore-and-matchcomponents):
  a three-a-week plan ties a two-a-week one against a target of `2`, so only
  the order tells them apart.

### `guaranteeSlate` and the direct fill

When *every* relaxed cadence also fails — the supplier works no Fridays at
all, say, and you've set `allowWeekdaySubstitution: false` so Friday can
never be dropped — `guaranteeSlate: true` adds one last floor: a **direct
fill**. All N sessions are picked straight from the supplier's real openings,
one per day, at the most consistent start time available, following **no
recurrence rule at all**.

Direct-fill slates are recognisable by two fields:

```json
{
  "cadenceRrule": null,
  "cadenceRelaxation": "DIRECT_FILL"
}
```

<Warning>
**`guaranteeSlate` guarantees flexibility of *cadence*, not of *capacity*.**
The name promises more than it delivers if you read it quickly. A supplier
who simply doesn't have N open days still yields no complete plan — there is
no cadence clever enough to invent time that isn't there. When that happens
the under-filled plan is surfaced (or not) through `partial`, governed by the
project's `suggestionConfig.allowPartialPackages` setting, exactly as it is
today. `guaranteeSlate` does not override that setting, and it is not a
guarantee that you always get a slate.
</Warning>

## Schedule preferences: `daysOfWeek` and `excludeDates`

`package-slate` and `package-options` both also take two fields that narrow
*which* calendar days a session is allowed to land on, on top of the cadence
itself.

### `daysOfWeek` is a hard filter, not a preference

`daysOfWeek` is an **allow-list** of weekdays sessions may fall on, using the
convention `0 = Sunday … 6 = Saturday`:

```json
{ "daysOfWeek": [1, 2, 3, 4, 5] }
```

It's enforced **before** the planner ever looks at the supplier's
availability: a weekday you leave out is removed from the pool the engine
plans against, not filtered out of a result afterward. That has one
consequence worth stating plainly — **[cadence relaxation](#cadence-relaxation)
cannot reintroduce a day `daysOfWeek` excludes.** Every fallback cadence
`cadenceFlexibility` can produce, including the
[direct fill](#guaranteeslate-and-the-direct-fill) `guaranteeSlate` reaches,
still plans only inside the allowed weekdays. A UI's "No Sundays" choice stays
honoured even when the planner has to work harder to fill the package.

<Warning>
**`daysOfWeek` is an allow-list, not a block-list.** If your UI collects
exceptions the other way around — "No Sun / No Mon" chips a client toggles
*on* to exclude those days — you must invert the selection before calling
the API: send the days that remain (`[2, 3, 4, 5, 6]`), not the two the
client excluded. Sending the excluded days directly restricts the plan to
almost nothing instead of almost everything — the obvious integration bug
here.
</Warning>

Omit `daysOfWeek` entirely to allow any day.

<Note>
**Same field name, opposite behaviour on `/availability/suppliers`.** This
hard-filter behaviour is specific to `package-slate` and `package-options`.
On [`POST /availability/suppliers`](/guides/search-suppliers-by-availability#rank-suppliers-by-fit-availabilitymatch),
`daysOfWeek` is a **ranking preference**, not a filter — a weekday you leave
out is never removed from a supplier's slots, it only lowers that supplier's
`availabilityMatch` score. Check which endpoint you're calling before you
carry an integration's `daysOfWeek` handling over from one to the other.
</Note>

### `excludeDates` blocks specific local dates

`excludeDates` is a list of individual local calendar dates that must not
carry a session:

```json
{ "excludeDates": ["2026-08-20", "2026-08-21", "2026-08-22"] }
```

- **Dates are LOCAL**, matching how the planner buckets slots — a
  `YYYY-MM-DD` string matched against each slot's own local calendar date as
  the planner buckets it, not a UTC instant.
- **Each date is passed individually — there is no range form.** A five-day
  trip is five entries in the array, not a `{ from, to }` pair.
- **Maximum 90 dates** per request.

### The synergy: a blackout doesn't have to mean a refusal

Blacking out enough dates to make the *exact* requested cadence unfillable
used to mean the request came back a flat `422 NO_COMPLETE_SLATE` — even if
the supplier had plenty of other open time. With `cadenceFlexibility` opted
in, the same blackout can now produce a **relaxed-cadence plan** instead of
a refusal.

Take the same supplier as the [worked example](#worked-example) above —
Monday–Friday, 09:00–17:00, in `America/Toronto` (`-04:00` in July), on a
schedule that runs `2026-07-06` (a Monday) through `2026-08-03`. This time
request eight sessions, twice a week, on Mondays and Fridays:

```json
{
  "packageId": "pkg_01kvr4cgb3esg8hxx32kwhre7g",
  "timezone": "America/Toronto",
  "lookAheadStartDate": "2026-07-06T00:00:00-04:00",
  "rrule": "FREQ=WEEKLY;BYDAY=MO,FR;COUNT=8",
  "cadenceFlexibility": "FALLBACK"
}
```

Without any exclusions, that cadence fills cleanly — eight sessions on Jul
6, 10, 13, 17, 20, 24, 27, and 31. Now black out the third week's Monday and
Friday:

```json
{ "excludeDates": ["2026-07-20", "2026-07-24"] }
```

That removes 2 of the 8 occurrences the exact cadence needs. The rest of
the ~4-week schedule has only 7 more Monday/Friday slots to draw from (4
Mondays + 3 Fridays — the next Friday, Aug 7, falls after the schedule
ends), one short of the 8 requested. **No occurrence set of the exact
`MO,FR` cadence can complete, from any start date** — every prior version of
this endpoint would `422` here.

With `cadenceFlexibility: "FALLBACK"` set, the response instead comes back:

```json
{
  "status": "ALTERNATIVE_CADENCE",
  "reason": "no complete slate at the requested cadence; returning alternative cadences",
  "suggestionRequestId": "sugreq_01kx16ej7pe4r9da74adf6m4h0",
  "resolvableUntil": "2026-07-07T12:00:00.000Z",
  "primarySlate": null,
  "alternates": [],
  "partial": null,
  "cadenceAlternatives": [
    {
      "slateId": "slate_01kx16ejsqffc9rbgdcc591w2p",
      "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
      "completeness": "COMPLETE",
      "sessionsRequested": 8,
      "sessionsFilled": 8,
      "startTimeConsistencyPercent": 100,
      "matchScore": 0.5,
      "matchComponents": { "startDate": 1, "cadence": 0 },
      "totalTravelTimeMins": 0,
      "cadenceRrule": "FREQ=WEEKLY;BYDAY=MO,TU,WE,FR;COUNT=8",
      "matchesRequestedCadence": false,
      "cadenceRelaxation": "DAYS_ADDED",
      "slots": []
    }
  ],
  "requestedCadence": "FREQ=WEEKLY;BYDAY=MO,FR;COUNT=8"
}
```

(`cadenceAlternatives[0].slots` abridged to `[]` here, the same convention
as [Anatomy of a slate](#anatomy-of-a-slate) above. `cadenceDistance` — present
on a real response here, since it's stamped whenever relaxation was requested —
and [`cadenceSummary`](#how-often-a-plan-runs-cadencesummary), which is present
on every response whether relaxation was requested or not, are left out too:
their exact numbers depend on which admissible cadence the engine actually
picks, which the underlying test doesn't pin down. Every other field is real:
`reason` always carries that exact string whenever `status` is
`ALTERNATIVE_CADENCE`; `suggestionRequestId` and `resolvableUntil` are
present because `persist` defaults to `true`; `requestedCadence` is present
because `cadenceFlexibility` was set to anything other than `NONE` — it
echoes `rrule` verbatim.) `matchScore` is `0.5` for the same reason as the
[worked example](#worked-example) above: `DAYS_ADDED` scores `cadence` at
`0`, averaged with `startDate`'s `1`.

`primarySlate` is `null` — the exact requested cadence is genuinely
unfillable — but `cadenceAlternatives` carries at least one **COMPLETE**
plan (all 8 sessions, none of them on an excluded date), sorted
closest-first, at a denser cadence that finishes before ever reaching the
blackout week. (The exact alternate depends on the supplier's real
openings — adding Tuesday and Wednesday, shown above, is one admissible
rung that reaches 8 sessions by day 12, well ahead of the July 20
blackout.) A request that used to be a dead end now returns a workable,
shifted plan.

<Note>
`daysOfWeek` and `excludeDates` are accepted by `package-options` too, with
identical semantics — it plans every ACTIVE package the same way
`package-slate` plans one.
</Note>

## Path A: book explicit sessions (transcribe)

The primary path — passing `{ slateId }` to `POST .../package-bookings` — is
what [Create a package booking](/guides/create-a-package-booking) walks
through, and it's the one to reach for by default: the server re-resolves
every session itself.

Path A is the fallback for when you need to alter or filter individual
sessions before booking (for example, dropping one session from an
8-session slate, or swapping in a client-chosen alternate time you resolved
separately). Instead of `slateId`, you build a `sessions[]` array yourself
by copying each slot from the slate response:

```ts
// Map each resolved slot to a `sessions[]` entry — VERBATIM.
function transcribeSlot(slot: PackageSlot) {
  return {
    supplierId: slot.supplierId,
    bookingStartUtc: slot.bookingStartUtc,
    bookingEndUtc: slot.bookingEndUtc,
    bookingTz: slot.bookingTz,
    locationType: slot.locationType,
    locationId: slot.locationId,
    latitude: slot.latitude,
    longitude: slot.longitude,
    address: slot.address,
    services: [{ serviceId: slot.serviceId, offeringId: slot.offeringId }],
  };
}

const sessions = primarySlate.slots.map(transcribeSlot);

await fetch(`${MARKETBOX_API_URL}/v1/projects/${MARKETBOX_PROJECT_ID}/orders/${orderId}/package-bookings`, {
  method: 'POST',
  headers: { 'x-api-key': MARKETBOX_API_KEY, 'content-type': 'application/json' },
  body: JSON.stringify({
    orderItemId,
    idempotencyKey: crypto.randomUUID(),
    atomicity: 'all_or_nothing',
    sessions,
  }),
});
```

<Warning>
**Copy each slot verbatim — do not re-derive locations.** A `TRAVEL_ZONE`
slot's `locationId` is the supplier's *resolved travel zone*, computed by
the slate engine specifically for that supplier and location. Recomputing
it yourself (e.g. re-resolving from raw `lat`/`lng`) can silently select the
wrong zone and mis-place the booking by a meaningful distance. Take the slot
fields as-is; only omit or reorder whole sessions, never recompute their
contents.
</Warning>

`slotId`, `sessionIndex`, `travelTimeMins`, `capacity`, and the deprecated
`reservationStatus` are **not** part of a session entry — they're slate
metadata, not booking input. Only the fields listed above go into
`sessions[]`.

Provide **exactly one** of `sessions`, `slateId`, or `slotIds` on
`POST .../package-bookings` — sending more than one (or none) is a `400
VALIDATION_ERROR`.

## Path B: hold, then convert

Both `slateId` and Path A book immediately. If you need to **hold the
sessions while the client pays** — a timed checkout — don't book at all:
hold the slate, take payment, then convert the hold into bookings.

Holds are no longer a package-only concept, and they no longer live under
`/suggestions`. A hold is a standalone claim on supplier time
(`POST /v1/projects/{projectId}/holds`), and it takes **exactly one** of
`intervals` (explicit supplier time — this is how you hold a *single*
session, with no package or slate anywhere), `slateId` (every slot of the
slate you just built), or `slotIds` (a cherry-picked subset). Convert is a
single endpoint for both shapes. The whole lifecycle — hold, heartbeat,
convert, release, and the `SLOT_HELD` error you get if you try to book held
time directly — is covered in
[Hold slots during checkout](/guides/hold-slots-for-checkout).

Holding by `slateId` / `slotIds` takes **no location fields**: the slate's
persisted slots already carry `bookingTz`, `locationType`, `locationId`,
coordinates and `address`, and the hold copies them onto the reservation —
the same reason book-by-`slateId` needs no `address`. The explicit
`intervals` form is the one that must supply them itself (`bookingTz` and
`locationType` are required on every interval).

<Warning>
A live hold blocks the time it claims: the slot stops being returned by
availability search, and a direct `POST .../package-bookings` over it fails
with `409 SLOT_HELD` — **even when the hold is your own**. If you hold, you
convert. See [Concurrency](/concepts/concurrency).
</Warning>

| Endpoint | Method | Auth | Description |
| --- | --- | --- | --- |
| `/v1/projects/{projectId}/availability/search` | `POST` | `x-api-key` | Single-session slot search. Full reference: [Availability](/resources/availability). |
| `/v1/projects/{projectId}/availability/time-slots` | `POST` | `x-api-key` | Direct engine invocation. Full reference: [Availability](/resources/availability). |
| `/v1/projects/{projectId}/availability/suppliers` | `POST` | `x-api-key` | Paginated suppliers, each with open slots grouped by local day. Full reference: [Availability](/resources/availability). |
| `/v1/projects/{projectId}/availability/package-slate` | `POST` | `x-api-key` | Build an N-session slate for a package from one supplier. `422` only when `primarySlate`, `partial` **and** `cadenceAlternatives` are all empty — a bookable `cadenceAlternatives` makes it a `200`. |
| `/v1/projects/{projectId}/availability/package-options` | `POST` | `x-api-key` | Plan **every** ACTIVE package of a service in one call. Always `200` — an unbookable package carries its own `status` + `reason` instead of failing the request. Accepts the same cadence-relaxation fields. |
| `/v1/projects/{projectId}/orders/{orderId}/package-bookings` | `POST` | `x-api-key` | Book via `sessions` (Path A), `slateId`, or `slotIds` — exactly one. |
| `/v1/projects/{projectId}/holds` | `POST` | `x-api-key` | Hold supplier time — `intervals`, `slateId`, or `slotIds` (exactly one). Returns `reservationId` + `heldUntil`. See [Hold slots during checkout](/guides/hold-slots-for-checkout). |
| `/v1/projects/{projectId}/holds/{reservationId}/convert` | `POST` | `x-api-key` | Convert a hold into confirmed bookings. Idempotent — safe for webhooks. |
| `/v1/projects/{projectId}/holds/{reservationId}/release` | `POST` | `x-api-key` | Release a hold. Idempotent — always `200`. |

### Errors and edge cases

| Scenario | `code` | Status | Resolution |
| --- | --- | --- | --- |
| `rrule` has no bounded `COUNT` | `VALIDATION_ERROR` | `400` | Add a positive `COUNT`, e.g. `FREQ=WEEKLY;BYDAY=MO;COUNT=8`. |
| `lookAheadStartDate` has a `Z` suffix instead of a numeric offset | `VALIDATION_ERROR` | `400` | Use a numeric `±HH:MM` offset, e.g. `-04:00`. |
| Cadence needs more than 120 days to fit the package's `creditCount` sessions, and `cadenceFlexibility` is `NONE` | `NO_COMPLETE_SLATE` | `422` | `reason` names the exact window required. Use a denser cadence (more days per week), fewer sessions per call, or set `cadenceFlexibility` — with flexibility on, the window **clamps to 120 days and the engine runs**, since a denser cadence needs a shorter window. |
| No availability at all for the requested window/location | `NO_AVAILABILITY` | `422` | Try a different location, timezone, or `lookAheadStartDate`. |
| No complete single-supplier slate under the project's supplier policy | `NO_COMPLETE_SLATE` | `422` | Check `alternates`/`partial` in the response first — they may still be usable. Set `cadenceFlexibility` to also get complete plans at a denser cadence in `cadenceAlternatives`. Otherwise widen the window or location. |
| Provided more than one (or none) of `sessions` / `slateId` / `slotIds` on booking or holding | `VALIDATION_ERROR` | `400` | Provide exactly one. |
| The referenced slate/slot doesn't exist, has no slots, or is past its 24-hour resolvable window (**holding only**) | `SLATE_NOT_FOUND` / `SLOT_NOT_FOUND` / `SUGGESTION_EXPIRED` | `409` | Rebuild the slate with `POST /availability/package-slate` and hold the fresh one. |
| Chosen slot went stale between building a slate and booking it directly (`slateId`/`slotIds`, no hold) | `SLOT_NO_LONGER_BOOKABLE` | `409` | The response includes `freshSuggestions` — rebuild from it. Covered in depth in [Create a package booking](/guides/create-a-package-booking#reference). |
| The time is claimed by a live hold — including your own, if you tried to book it directly instead of converting | `SLOT_HELD` | `409` | `conflicts[0].reservationId` names the hold. Convert it, or offer another slot. See [Hold slots during checkout](/guides/hold-slots-for-checkout#handling-a-held-slot). |
| The time is claimed by a confirmed booking | `SLOT_BOOKED` | `409` | Rebuild the slate — the supplier is taken. |
| More than 15 sessions with `atomicity: "all_or_nothing"` (applies to direct booking and convert alike) | `PACKAGE_SLATE_TOO_LARGE_FOR_ATOMIC` | `422` | Use `atomicity: "best_effort"` (requires `suggestionConfig.allowPartialPackages`), or book/hold a smaller slate. |
| `best_effort` requested but the project hasn't enabled it | `BEST_EFFORT_NOT_ENABLED` | `422` | Stay with `all_or_nothing` (≤15 sessions), or ask the project to enable `suggestionConfig.allowPartialPackages`. |

<Warning>
**The granular stale codes above (`SLATE_NOT_FOUND`, `SLOT_NOT_FOUND`,
`SUGGESTION_EXPIRED`) are returned verbatim only by `POST /holds`.** At
booking time — `POST .../package-bookings` by `slateId`/`slotIds` — every
one of these same stale conditions is collapsed to a single
`code: "SLOT_NO_LONGER_BOOKABLE"` (the `message` still names the specific
cause). Branch on the distinct codes only when you're calling the holds
endpoint; for direct booking, branch on `SLOT_NO_LONGER_BOOKABLE` alone.
</Warning>

See [Errors](/concepts/errors) for the full envelope and code list,
[Concurrency](/concepts/concurrency) for supplier-time conflicts, and
[Create a package booking](/guides/create-a-package-booking#reference) for
the errors specific to the order/order-item side of booking (expired
packages, insufficient quantity, and so on) — convert shares that same
booking path and can return the same set.
