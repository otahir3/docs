<Update label="September 24, 2026" tags={["API"]}>

## Package purchases are taxed, and order tax is computed, not set

The platform now computes every order's tax, and package lines are taxed like any other line. A line with no tax says why. `PATCH …/orders/{orderId}` no longer lets you overwrite tax.

**One breaking change, the rest a behaviour change and additive fields.** No field was removed or renamed. Strict response decoders need a regeneration for `taxExemptReason` on order items.

**Breaking**

- **`tax` on `PATCH …/orders/{orderId}` can no longer change the order.** It is accepted only when it equals both the tax the lines compute and the tax the order stores. Any other figure is `400 TAX_MISMATCH`, and nothing is written. The same code is returned when the order has lines in a different currency. Omit `tax`.

**Changed**

- **Package lines are taxed.** A `PACKAGE` line now takes the tax its price rule resolves, like a single-session line. Package lines written between June and September 2026 keep their zero tax.
- **The service's tax settings are the last fallback.** When neither the matched price rule nor its parent rules set tax, a line uses the service's `taxSettings`. Lines that used to carry no tax can now be taxed.
- **A taxable fee borrows the rate of the first line taxed at a positive rate.** Untaxed and 0% lines no longer shadow a taxed line listed after them, so line order no longer changes a fee's tax.

**New**

- **`taxExemptReason` on order items** — why a line carries no tax: `NO_RATE`, `NOT_TAXABLE`, `ZERO_RATE`, `MIGRATED_V1` or `PACKAGE_EXEMPT_LEGACY`. Absent when the line is taxed at a positive rate, and on lines written before the field existed.

**What this means for you**

- **Stop sending `tax` on `PATCH …/orders/{orderId}`.** Handle `400 TAX_MISMATCH` if you can't remove it yet.
- **Show the tax the API returns on package checkouts.** Package totals now include tax where the price rule or service sets a rate.
- **Branch on `taxExemptReason`, not on `skuType`,** to explain a zero tax.

Full detail: [Orders → How tax is computed](/resources/orders#how-tax-is-computed), [Orders → Updating an order](/resources/orders#updating-an-order), [Service fees → A taxable fee borrows the rate of a taxed line](/concepts/service-fees#a-taxable-fee-borrows-the-rate-of-a-taxed-line), [Errors](/concepts/errors).

</Update>

## Orders settle from the ledger, cancels settle the credit, and clients carry their real names

This release makes money and credit follow one rule. An order becomes `PAID` only when its ledger covers its total. Cancelling a package session returns or forfeits its credit in the same write. Onboarding also accepts the name your checkout collected, so a client who signed up with an email address is no longer shown under the part before the `@`.

**Three breaking changes, the rest additive.** No field was removed or renamed. See **Breaking** below. Strict response decoders need a regeneration for the new booking, order, order-item, transaction and client-address fields.

**Breaking**

- **`PAID` can no longer be requested.** `POST …/orders/{orderId}/status` answers a `PAID` target with `409 ORDER_NOT_SETTLED`. An order becomes `PAID` when its ledger covers its total: record cash, external or comp money with `POST …/orders/{orderId}/transactions`, and let the Stripe webhook settle cards. `PENDING` → `PAID` is gone from the transition list.
- **`NO_SHOW` can no longer be set.** Sending it to `POST …/bookings/{bookingId}/status` is a `400`. Send `CLIENT_NO_SHOW` or `SUPPLIER_NO_SHOW`. Bookings recorded before the split still carry `NO_SHOW` on every read, and will indefinitely.
- **An order line the service is not sold as is refused.** `POST …/orders` and `POST …/orders/{orderId}/items` return `422 SERVICE_NOT_SOLD_AS` when the service has no active rate of the line's kind, such as a `SINGLE_SESSION` line with no active `SINGLE_BOOKING` rate. Such lines used to be written with no rate attached, and so without its fees.

**New**

- **`firstName` and `lastName` on `POST …/clients/me`**, beside `phone`. Each field you send overwrites the stored value and is copied to the client's record in Stripe. Blank or `null` means not sent. At most 80 characters after trimming.
- **`PATCH …/clients/me`** — change the signed-in client's `firstName`, `lastName` or `phone`. Names can be changed but not cleared; `phone: null` clears the phone. Call it before `POST /orders` so emails use the new name.
- **`creditTreatment` on `POST …/bookings/{bookingId}/status`**, with `CANCELLED` only. `RETURN` (the default for a package session) puts the session back on the order item and records a `CREDIT_REVERSAL`. `FORFEIT` keeps it spent. Sending it for a booking with no package credit is `422 NO_SESSION_CREDIT`, and nothing is cancelled.
- **Three listing modes on `GET …/orders`.** `status` is no longer required. Send `status`, or `paymentMethod` (with `startSettledAt`/`endSettledAt`), or neither to list every order (with `startCreatedAt`/`endCreatedAt`). Mixing modes is a `400`. The no-filter mode is missing orders created before this release until a backfill runs.
- **`reason` and `idempotencyKey` on `POST …/orders/{orderId}/transactions`.** `reason` is required with `source: "COMP"`. The same `idempotencyKey` on the same order returns the first row as `200` with `replayed: true` instead of recording the money twice. A first recording is `201` with `replayed: false`.
- **`skills` on `POST …/availability/search`** — supplier skill ids a supplier must all hold to be considered.
- **`bio: null` on `PUT …/suppliers/{supplierId}`** clears the bio. Omitting it still keeps it.
- **New response fields.**
  - Order: `paymentMethod`, `settledAt`, `amountComped`.
  - Order item: `priceSource` (`RULE` or `MANUAL`).
  - Booking: `creditTreatment`, `cancellationInitiatedBy`, `cancellationReasonCode`, `durationOverrideMinutes`, `durationOverrideReason`.
  - Transaction: `channel`, `reason`, and the `CREDIT_REVERSAL` kind.
  - Client address: `latitude`, `longitude`.

**Changed**

- **Cancelling settles the order item.** A cancelled package session returns its credit by default. A cancelled single session closes its allocation and returns no quantity. `DELETE …/bookings/{bookingId}` settles the same way as a default cancel.
- **The card is saved on public-API checkout.** When the order's client has an email, the PaymentIntent sets `setup_future_usage: off_session`. Tell the client their card will be saved.
- **Body ids are fenced to your project.** A `clientId` or `supplierId` from another project is a `404` with nothing written, on booking create and update, participants, order create, package bookings, holds and manual transactions.
- **A booking line must match its order item's kind.** A `businessModelType` the order item is not sold as is `400 ORDER_ITEM_BUSINESS_MODEL_MISMATCH`.
- **Cancellation emails** report what happened to the client's session credit, and do not include the `cancellationReason` text.

**What this means for you**

- **Stop setting orders to `PAID`.** Record the payment instead, and read `status` back.
- **Send an `idempotencyKey`** on every manual transaction you might retry, and branch on `replayed`.
- **Send `reason` with every comp.**
- **Replace `NO_SHOW` in requests** with `CLIENT_NO_SHOW` or `SUPPLIER_NO_SHOW`. Keep handling it in responses.
- **Decide your late-cancel policy.** Send `creditTreatment: "FORFEIT"` when a package session should stay spent. Otherwise it goes back to the client.
- **Send `firstName` and `lastName` on onboarding**, especially for email-and-password sign-ups.
- **Handle `422 SERVICE_NOT_SOLD_AS`** on order create, and check the rates on services you sell.
- **Don't treat the no-filter orders list as complete** for historical data. List by `status` when you need every order.
- **Tell clients at checkout that their card will be saved.**

Full detail: [Orders → Settling an order](/resources/orders#settling-an-order), [Orders → Listing orders](/resources/orders#listing-orders), [Bookings → Cancelling and the package credit](/resources/bookings#cancelling-and-the-package-credit), [Booking flow auth → Onboard the client](/guides/booking-flow-auth#onboard-the-client), [Errors](/concepts/errors).

## Every slot time is one instant, every zone is IANA, and bookings say who moved them

Availability slots used to take their clock digits from the supplier's own zone and their offset from the `timezone` you passed, so when the two differed the string described a different moment than the one the supplier was free at — a Toronto supplier viewed with `timezone: "America/Los_Angeles"` was three hours off. Recurring schedules also used one fixed offset for their whole span and drifted an hour after a daylight-saving change. Both are fixed, and the booking lifecycle now carries the statuses the platform has been using internally.

**Additive on the wire, with one breaking validation change.** No field was removed or renamed. A request that previously sent an abbreviated timezone will now be rejected — see **Breaking** below. Strict response decoders need a regeneration for the new booking statuses and the new slot and envelope fields.

**New**

- **`timeSlotStartUtc` on every slot** in `timeSlots[]` and `openSlots[]` from `POST /v1/projects/{projectId}/availability/search` and `…/time-slots`. The slot start in UTC, always `Z`-suffixed, always the same instant as `timeSlotDateAndTime`. Prefer it as the booking anchor. Package slates derive each session's `bookingStartUtc` from it. This is a response shape:

```json
{
  "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
  "timeSlotDateAndTime": "2026-11-08T09:00:00-05:00",
  "timeSlotStartUtc": "2026-11-08T14:00:00.000Z"
}
```

- **`supplierZones` on `POST /v1/projects/{projectId}/availability/search`** — each returned supplier's own profile zone, keyed by `supplierId`. The recommended `bookingTz` for a virtual booking with no service location: location zone, else supplier zone, else project default. A supplier missing from the map has no profile zone.
- **Four booking statuses**: `AWAITING_CONFIRMATION`, `DISPUTED`, `CLIENT_NO_SHOW`, `SUPPLIER_NO_SHOW` — on every booking response and on the `status` filter of the three list endpoints. `AWAITING_CONFIRMATION` and `DISPUTED` are entered by the platform after a session ends and can only be observed. `CLIENT_NO_SHOW` / `SUPPLIER_NO_SHOW` replace `NO_SHOW`, which no longer said which side was absent. See [Bookings → The booking lifecycle](/resources/bookings#the-booking-lifecycle).
- **`statusUpdatedBy` and `statusUpdatedByCapacity` on every booking** — who last changed the status and in what capacity (`ADMIN`, `SUPPLIER`, `CLIENT`, `SYSTEM`, `API`). A change made through the public API is attributed to the API key that made it, in the `API` capacity.
- **`lookAheadStartDate` accepts a `Z` instant on recurring `…/availability/search`.** A `Z` suffix and a numeric offset are equally valid there; the "must carry a numeric offset" `400` is gone from that endpoint. `…/package-slate` and `…/package-options` still require a numeric offset.

**Changed**

- **Corrected slot times.** `timeSlotDateAndTime` keeps its name and now renders the slot instant in the response `timezone` with that zone's offset **at that instant**, so digits and offset always agree and the string always parses to `timeSlotStartUtc`. If your code parses the whole string you will simply see correct times. If it reads only the clock digits, pass `timezone` explicitly to keep receiving that zone's clock. On `…/availability/suppliers`, `startUtc` is now the engine instant verbatim and `startLocal` is rendered in the response `timezone`.
- **Daylight saving.** A supplier's weekly schedule now keeps its local wall clock across a transition (a 9:00 lesson stays 9:00 in the supplier's zone) and the UTC instant shifts. That is correct; do not "fix" it on your side.
- **Package sessions are stamped with the home zone.** Slots from `…/package-slate` and `…/package-options`, and the bookings created from them, carry `bookingTz` equal to the session's home zone — the service location's zone, else the supplier's, else the project default — instead of the `timezone` you sent. `bookingStartUtc` is unchanged.
- **Recurring search windows resolve on the local date.** On recurring `…/availability/search`, the window and the recurrence anchor are read on the local date in the request `timezone`, so a midnight-UTC `lookAheadStartDate` against a zone west of Greenwich anchors one day earlier than before. A value that does not parse is a `400` in the standard error envelope rather than a raw validation payload.
- **`POST …/bookings/{bookingId}/status` request enum is narrower than the response.** `SCHEDULED` and `DISPUTED` are no longer advertised as settable — they were always rejected. `NO_SHOW` is **deprecated**, still accepted, and will be removed in a later version. An API key can request every transition an operator can except resolving a dispute or reversing a settled booking back to `AWAITING_CONFIRMATION`. A transition the booking cannot make is a `400` naming the booking's current status.
- **Supplier `timezone` drives the daily agenda email.** It is used verbatim as the schedule zone for the supplier's 07:00 agenda; unset inherits the project default.

**Breaking: timezone values must be IANA identifiers**

Every zone field is validated on write. Accepted: any IANA identifier containing a `/` (`America/Toronto`, `Australia/Sydney`, `Asia/Kolkata`) and the literal `UTC`; deprecated aliases with a `/` (`US/Pacific`) still pass. **Rejected with `400 VALIDATION_ERROR`:** abbreviations (`EST`, `PST`, `IST`, `CET`), legacy names without a `/` (`Hongkong`, `Japan`), numeric offsets (`-05:00`), and values with surrounding whitespace. The message names the field:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "bookingTz: Must be an IANA timezone identifier such as America/Toronto (abbreviations like EST are not accepted)",
  "statusCode": 400,
  "requestId": "e21d9f4a-6b8c-4e3d-a175-2c9f6b0d8a53"
}
```

| Endpoint | Field |
| --- | --- |
| `POST …/availability/search`, `…/suppliers`, `…/package-slate`, `…/package-options` | `timezone` |
| `POST …/bookings`, `PATCH …/bookings/{bookingId}` | `bookingTz` |
| `POST …/holds` | `intervals[].bookingTz` |
| `POST …/orders/{orderId}/package-bookings` | `bookingTz` |
| `POST …/suppliers`, `PUT …/suppliers/{supplierId}` | `timezone` |

Stored values are not re-validated on read.

**What this means for you**

- **Search your code for hard-coded zone strings** sent to the API and replace abbreviations with IANA ids: `EST` → `America/Toronto` or `America/New_York`, `PST` → `America/Los_Angeles`, `IST` → `Asia/Kolkata`.
- **Prefer `timeSlotStartUtc`** for anything that computes with a slot time; treat `timeSlotDateAndTime` as a display convenience.
- **If you rely on the clock digits** in `timeSlotDateAndTime`, pass `timezone` explicitly on every availability request.
- **If you display package sessions using `bookingTz`**, expect the home zone rather than your request zone.
- **Regenerate response types** for the four new statuses, `statusUpdatedBy`, `statusUpdatedByCapacity`, `timeSlotStartUtc` and `supplierZones`. Handle `AWAITING_CONFIRMATION` and `DISPUTED` as in-flight, not failed.
- **Stop sending `NO_SHOW`.** Send `CLIENT_NO_SHOW` or `SUPPLIER_NO_SHOW` instead.
- **A "no `Z`" guard on `lookAheadStartDate` is now only needed for the package endpoints**, not for recurring search.

Full detail: [Timezones](/concepts/timezones), [Availability → Slot times and zones](/resources/availability#slot-times-and-zones), [Bookings → The booking lifecycle](/resources/bookings#the-booking-lifecycle).

</Update>

## Supplier directory: `servedRegions`, point search, one liveness rule — plus booking locale and E.164 phones

You can now see exactly why a supplier does or does not match the region filter, search the directory by coordinate, and record the language a purchase was made in.

**Purely additive on the wire, with one behaviour change.** No field was removed or renamed and every request valid before this release is still valid. `servedRegions` is a **new required field** on every supplier response, so strict response decoders need a regeneration. The liveness change below can make `locations[]` shorter than it was.

**New**

- **`servedRegions` on every supplier response** — the rows of `GET /v1/projects/{projectId}/suppliers`, the detail endpoint, the create, update, services, skills and avatar responses, and `data[].supplier` on `POST /v1/projects/{projectId}/availability/suppliers`. Sorted slug region paths at every hierarchy level — the **same set** the `country`/`state`/`city` filter matches against, so membership is explainable from the record. `[]` when there is no live schedule with a geocodable zone. This is a response shape:

```json
{
  "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
  "phone": "+14165550142",
  "locations": [
    { "locationId": "stz_01kv60qgnef2kt3pvqgwmkbzfr", "locationType": "TRAVEL_ZONE", "name": "Scarborough" }
  ],
  "servedRegions": ["ca/", "ca/on/", "ca/on/scarborough/", "ca/on/toronto/"],
  "defaultLocale": "fr-CA"
}
```

- **`lat` + `lng` on `GET /v1/projects/{projectId}/suppliers`** — both or neither. Returns suppliers whose **live travel zone contains the point**, tested against the real polygon or radius, AND-combined with `services`/`skills`. Exclusive with `country`/`state`/`city` (`400`). Fixed-location-only suppliers have no zone and are not matched by a point. The first way to ask "who covers this address?" without a service and an offering.
- **Borough matching.** Coverage now resolves to the locality, its borough and the wider municipality, so a Scarborough zone is returned by `city=Scarborough` **and** `city=Toronto`. Previously only the municipality matched.
- **`locale` on `POST /v1/projects/{projectId}/orders`** — optional, the language the buyer completed the purchase in. Normalized to canonical BCP-47 (`en-us` → `en-US`); malformed is a `400 VALIDATION_ERROR`. Immutable on the order, snapshotted as `locale` onto every booking the order funds (never accepted on `POST /bookings`), and saved as the client's `defaultLocale` (latest booking wins). Suppliers gain a staff-set `defaultLocale` on create and update (`null` clears on update) and in every response — distinct from the existing `languages` and derived `locales`.
- **Three review-URL tokens** beside `{bookingId}`: `{bookingLocale}`, `{clientLocale}`, `{supplierLocale}`. Each falls back only to the project default, never to another token. See [Emails](/concepts/emails#where-the-rating-links-go).

**Changed**

- **One schedule-liveness rule.** A schedule is live when it is `ACTIVE`, not deleted, **and its `endDate` has not passed in the schedule's own timezone**. `locations[]`, the region filter, `servedRegions` and the detail endpoint's `availability.schedules` all use it. Before this release `locations[]` and `availability.schedules` ignored `endDate`, so a supplier whose only schedule had ended still advertised a travel zone the filter no longer matched — in one real project, 80 records carried `country: "CA"` on their profile while `?country=CA` returned 49 rows. **`locations[]` and `availability.schedules` can now be shorter, including `[]`, for suppliers you saw as bookable yesterday.**
- **Supplier `phone` is validated and normalized.** Create and update accept E.164 or a national NANP number and store E.164 (`+14165550134`); anything unparseable is a `400 VALIDATION_ERROR`. Update accepts `null` to clear. Rows written before this release keep whatever was typed until next edited.

**What this means for you**

- **Regenerate response types.** `servedRegions: string[]` is required everywhere a supplier is returned.
- **Stop deriving "does this supplier serve Toronto?" from profile `city`/`state`.** Read `servedRegions`, or use the filter — they agree by construction. `locations[]` is per-request; `servedRegions` is swept daily and can lag a schedule's `endDate` by up to a day.
- **If you filter by `city`, expect more rows** where boroughs exist. Nothing you matched before stopped matching.
- **If you cached `locations[]` to decide bookability**, refresh: a schedule past its `endDate` no longer contributes. `schedules: []` on the detail endpoint now really means "cannot be booked".
- **Send `locale` on order create** if your storefront is localized and you use a review redirect URL — it is the only way MarketBox can learn the language, and the tokens fall back to the project default without it.
- **Don't pre-format phones**, and don't assume the stored value matches what you sent — read it back.

Full detail: [Suppliers → Regions served](/resources/suppliers#regions-served), [Listing suppliers](/resources/suppliers#listing-suppliers), [Orders → Creating an order](/resources/orders#creating-an-order).

</Update>

## Every slate now says why it isn't a perfect match: `matchNotes` and `advice`

`matchScore` told you how well a slate matched, and `matchComponents` told you which criterion missed. Neither told you **why** — so a booking UI could show "3 of 4 weeks" and had nothing to put underneath it. Slates now carry `matchNotes`: one coded reason per departure, each with the evidence behind it.

**Purely additive.** No existing field changed shape, meaning, or gating. Every request valid before this release is still valid, and every response field you already read is unchanged. This one is safe to adopt at your own pace — unlike the `cadenceSummary` release below it, which removed a field.

**New**

- **`matchNotes` on every slate** (`PackageSlateDto`) — an array of `{ code, component, weekStart?, evidence }` objects. **Always present**: nothing departed from your request means `[]`, not a missing key, so `.length` is safe to read without a null check. It is **not** gated on `matchScore` — a `DIRECT_FILL` slate and a `PARTIAL` slate can both score `1` and still carry notes, and those are exactly the slates worth captioning.

```json
{
  "matchNotes": [
    {
      "code": "WEEK_SUPPLY_INSUFFICIENT",
      "component": "sessionsPerWeek",
      "weekStart": "2026-09-14",
      "evidence": {
        "sessionsPlaced": 0,
        "sessionsTargeted": 4,
        "openingsInPool": 0
      }
    }
  ],
  "advice": {
    "code": "LATER_START_IMPROVES_CADENCE",
    "earliestSustainedWeek": "2026-09-21"
  }
}
```

- **Nine codes**, each with its own evidence shape, discriminated on `code` so your generated types tell you exactly which fields are present: `SUPPLIER_UNAVAILABLE_WEEK`, `WEEK_EXCLUDED_BY_FILTERS`, `WEEK_SUPPLY_INSUFFICIENT`, `WEEK_CAPPED`, `SESSIONS_EXHAUSTED`, `CADENCE_RELAXED`, `SESSIONS_OUTSIDE_PREFERRED_TIMES`, `FIRST_SESSION_LATE`, `PACKAGE_UNDERFILLED`.
- **`advice` on every slate**, optional — a forward-looking hint naming `earliestSustainedWeek`, the earliest Monday from which supply alone could sustain the frequency you asked for.
- Both fields appear at **all 17 slate positions** across the same four operations `cadenceSummary` reaches: `POST /v1/projects/{projectId}/availability/package-slate` (`200`), `POST /v1/projects/{projectId}/availability/package-options` (`200`), `POST /v1/projects/{projectId}/orders/{orderId}/package-bookings` (**`409`**, inside `freshSuggestions`), and `POST /v1/projects/{projectId}/suggestions/slots/{slotId}/reschedule` (`200` and **`409`**).

**Why there is no message string**

A note carries no English at all. You keep your own copy and can localise it; `evidence` exists so you can name the week, the weekday or the count in your own wording. Weekday numbers everywhere are `0` = Sunday through `6` = Saturday, matching request-level `daysOfWeek`.

**What this means for you**

- **"Wait a week" and "loosen your days" are opposite calls to action, and telling them apart is the point of the whole field.** The supplier-break case reaches you as `WEEK_SUPPLY_INSUFFICIENT` with `openingsInPool: 0` — nothing was open that week, relaxing your own filter cannot help, so "wait a week" is the honest thing to say and `advice` names which week. `WEEK_EXCLUDED_BY_FILTERS` is the reverse: the supplier's working pattern covers days in that week and your `daysOfWeek` or `excludeDates` cut them below your target, so "loosen your days" is the move. The candidate pool alone can't separate them, because your filters were already applied to it; `evidence.supplierWorkdays` is the pre-filter fact that can. Note it is a fact about the supplier's working **pattern**, not a check of that calendar week, so treat "loosen your filter" as the most likely fix rather than a guaranteed one.
- **`SUPPLIER_UNAVAILABLE_WEEK` is published but not currently emitted by the live engine.** It fires only for a supplier who works no weekday at all, and such a supplier yields no availability and therefore no slate for a note to attach to. Keep it in your `switch` — it is part of the contract — but key your "waiting helps" copy on `WEEK_SUPPLY_INSUFFICIENT` with `openingsInPool: 0` instead.
- **`SESSIONS_EXHAUSTED` means nothing went wrong — don't apologise for it.** Nine sessions at four a week leaves the last week holding one. That week is short because the package ran out of credits, not because anyone failed. It outranks every supply code, so when it's emitted for a week no supply code is emitted for that same week. Render it as a plain fact or drop it; surfacing it as a problem makes correct behaviour look broken.
- **`advice` is advisory and nothing more.** It reports that open supply exists from `earliestSustainedWeek` onward — **not** that a slate was built for that week, and not that one would be bookable. Holds, capacity, travel time and the cadence rules all still apply. Re-request with a later `lookAheadStartDate` before promising a client anything.
- **`matchNotes` explains `matchComponents`, it doesn't replace it.** Read `matchComponents` for *which* criterion missed and `matchNotes` for *why*; `component` on each note points at the criterion it explains. `PACKAGE_UNDERFILLED` is the one code with no `component`, because plan size isn't a scored criterion. That pointer is a guide, not a join key: the week-level codes bucket **Monday-anchored calendar weeks** while `matchComponents.sessionsPerWeek` buckets **consecutive 7-day blocks from your window's start**, so a note can name a short week for a criterion the component scores as met, and the reverse. Join notes to `cadenceSummary.byWeek` on `weekStart`, which shares their bucketing.
- Slates persisted before this release read back with `matchNotes: []` and no `advice`. Both are provenance — recorded when the slate was built, not re-derived on a rebuild.

Full walkthrough, with both sides of the supplier-versus-filter pair side by side: [Availability and slates → Why a slate departs from your request](/guides/availability-and-slates#why-a-slate-departs-from-your-request-matchnotes).

</Update>

## Slate cadence: `sessionsPerWeek` is gone, `cadenceSummary` replaces it

Every slate now reports how often it actually runs, week by week, instead of a single averaged rate.

**Breaking**

`sessionsPerWeek` has been **removed from the slate object** (`PackageSlateDto`) and replaced by `cadenceSummary`. This is only the slate *response* field: the request field of the same name (integer `1`–`14`, the frequency target) and `matchComponents.sessionsPerWeek` (the `0`–`1` match ratio) are **unchanged and still present**.

Before:

```json
{
  "slateId": "slate_01kx16ejsqffc9rbgdcc591w2p",
  "cadenceRrule": "FREQ=WEEKLY;BYDAY=MO,TU,WE,TH;COUNT=9",
  "sessionsPerWeek": 1.67
}
```

After:

```json
{
  "slateId": "slate_01kx16ejsqffc9rbgdcc591w2p",
  "cadenceRrule": "FREQ=WEEKLY;BYDAY=MO,TU,WE,TH;COUNT=9",
  "cadenceSummary": {
    "requested": 4,
    "peak": 4,
    "average": 2.25,
    "byWeek": [
      { "weekStart": "2026-09-07", "sessions": 1 },
      { "weekStart": "2026-09-14", "sessions": 0 },
      { "weekStart": "2026-09-21", "sessions": 4 },
      { "weekStart": "2026-09-28", "sessions": 4 }
    ]
  }
}
```

**Why**

The removed field was an average, and an average is the one number that describes none of the weeks. When a supplier takes a week off mid-plan, a nine-session plan lands 1 / 0 / 4 / 4 across four weeks — so the field reported `1.67`, and booking UIs rendered "1.67×/week" for a plan that runs at four a week wherever it runs at all. There was no way to recover the real cadence from that number, and no way to see *which* week was short.

`cadenceSummary` publishes the week-by-week truth instead. `peak` is the most sessions in any one week and is **the number to render**. `average` is `byWeek`'s sessions divided by `byWeek`'s length to two decimal places, verifiable straight from the array, counted across the plan's own span (first session's week through last session's) rather than your whole look-ahead window, so a wide window doesn't dilute it. `byWeek` is Monday-anchored, ascending and contiguous, and **includes weeks holding `0` sessions** — the zero week is how you show a client why a plan looks uneven instead of apologising for it. `requested` echoes the frequency you asked for: your `sessionsPerWeek` target when you sent one, otherwise the number of weekdays your own `FREQ=WEEKLY` rule named in `BYDAY`, and `null` when the rule wasn't yours to count (a non-weekly `FREQ`, an `INTERVAL` other than `1`, a weekly rule naming no weekdays, or a cadence this API synthesised for you).

**Changed**

- **Gating is wider than the field it replaces.** `sessionsPerWeek` was stamped only when cadence relaxation had been requested, so a strict caller could not get a cadence number at all. `cadenceSummary` is present on **every** request path, including the default `cadenceFlexibility: "NONE"`. It is absent only for a slate holding no sessions, which has no cadence to describe.
- **The swap spans 17 response positions across four operations**, not just the obvious one — every place a slate is published:
  - `POST /v1/projects/{projectId}/availability/package-slate` — `200`: `primarySlate`, `alternates[]`, `partial`, `cadenceAlternatives[]`.
  - `POST /v1/projects/{projectId}/availability/package-options` — `200`: the same four inside each entry of `data[]`.
  - `POST /v1/projects/{projectId}/orders/{orderId}/package-bookings` — **`409`**: the same four inside `freshSuggestions`.
  - `POST /v1/projects/{projectId}/suggestions/slots/{slotId}/reschedule` — `200`: `slate`. **`409`**: the same four inside `freshSuggestions`.

**What this means for you**

- **Read `cadenceSummary.peak` wherever you read `sessionsPerWeek`, and render `peak`.** Don't substitute `average` — that reproduces the bug this release fixes.
- **Update the `409` paths too, not just the availability calls.** Those bodies fire mid-checkout, when a slot went stale while a client was paying, and their `freshSuggestions` carries full slates. A client that reads the removed field only on the happy path fails at the worst possible moment.
- **`cadenceSummary` and `matchComponents.sessionsPerWeek` count weeks differently, deliberately.** `cadenceSummary` buckets Monday-anchored calendar weeks, so `weekStart` is always a real Monday and the buckets agree with the `maxSessionsPerWeek` cap. The `matchComponents` ratio buckets consecutive 7-day blocks from your window's start, so it stays comparable with `availabilityMatch` on `POST /availability/suppliers`. `peak: 4` against a target of `4` while that ratio reads below `1` is exactly the supplier-break case above, and both numbers are correct for what they measure — not a bug.
- **Unlike its neighbours, `cadenceSummary` is not provenance.** `matchScore` and `matchComponents` are recorded once and never re-derived, but `peak`, `average` and `byWeek` recompute from the slate's current sessions on every rebuild; only `requested` is snapshotted. A slate can come back from a reschedule with an unchanged `matchScore` and a changed `cadenceSummary`.
- Slates persisted before this release read back with `requested: null`; `peak`, `average` and `byWeek` are computed from their stored sessions, so they are correct.

Full explanation, with the two week-bucketings side by side: [Availability and slates → How often a plan runs](/guides/availability-and-slates#how-often-a-plan-runs-cadencesummary).

</Update>

## Package discovery, bookable package options, and a wider look-ahead window

Packages are now discoverable and plannable in one call each — and the weekly multi-session package that the engine used to refuse is bookable.

**New**

- **`GET /v1/projects/{projectId}/services/{serviceId}/packages`** — every package on a service, **across all of its offerings**. This is the call a storefront makes *before* the client picks an option, when it holds a `serviceId` and no `offeringId` — previously there was no endpoint that could answer it. Pass `?status=ACTIVE` for just the purchasable bundles. Each package carries its `offeringId`, so you can join it against the offerings list you already hold. A real service that sells no packages is a `200` with `data: []`; an **unknown** `serviceId` is a `404`, so a typo can never masquerade as "no packages".
- **`POST /v1/projects/{projectId}/availability/package-options`** — every ACTIVE package of a service, each planned against a supplier's real availability and carrying a ready-to-book `slateId`. Send a `serviceId` and a location (`locationId`, or `lat` + `lng` + `address`); `supplierId`, `timezone`, and `rrule` are optional. Cadence defaults to `FREQ=WEEKLY;COUNT={creditCount}`, derived **per package** from its own credit count. It replaces the client-side fan-out of one `package-slate` call per package, and it's cheaper than that loop — supplier bundles are read once per offering, not once per package.

**Changed**

- **The package look-ahead ceiling moved from 31 days to 120 days.** The window is still derived from your cadence and the package's `creditCount` — only the cap on that derivation changed. A weekly 10-session package spans about 70 days, so it was **unbookable** under the old 31-day cap and always came back `NO_COMPLETE_SLATE`; it now plans and books normally, as do weekly 12-packs (~84 days) and biweekly 5-packs (~70 days). A cadence that still needs more than 120 days keeps the existing fail-loud behaviour — `NO_COMPLETE_SLATE` with a `reason` naming the exact window required, never a silently truncated slate.

**What this means for you**

- If you were listing **business models** and rendering each row as a package, stop. `PACKAGE` is a business model — a flag meaning "this service *can* be sold as packages" — not a sellable bundle, and it carries no `creditCount` and no `pricing`. The bundles are what the new package list returns.
- If you hardcoded a dense weekday `rrule` (e.g. `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR`) purely to squeeze a multi-session package under the 31-day cap, you can drop the workaround and send the cadence you actually sell.
- Purely additive: no existing route, schema, or DTO changed shape. Every request valid before this release is still valid.

Walkthroughs: [Create a package booking with a slate](/guides/create-a-package-booking) (now starts at finding the package) and [Availability and slates](/guides/availability-and-slates) for the cadence rules and the new ceiling.

</Update>

## Holds, the double-booking guard — and a breaking change to `POST /holds`

Supplier time is now exclusive at the write layer, and you can **hold** it while a client pays. A hold works on any supplier time — a single session (no package, no slate), a cherry-picked subset of a package slate, or a whole slate — and `POST /holds/{reservationId}/convert` turns it into confirmed bookings. Alongside it, every write that claims supplier time now passes through an occupancy guard, so two bookings can never overlap on the same supplier.

**Breaking**

Each entry in `intervals[]` on `POST /v1/projects/{projectId}/holds` now mirrors the `POST /bookings` location contract exactly. **`bookingTz` and `locationType` are required**, and `locationType` decides which of `locationId` / `latitude` / `longitude` / `address` must come with them.

Before:

```json
{
  "intervals": [
    {
      "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
      "startUtc": "2026-07-15T14:00:00.000Z",
      "endUtc": "2026-07-15T15:00:00.000Z",
      "locationId": "stz_01kv60qgs4e4nbjhzradnqtj0h"
    }
  ]
}
```

After:

```json
{
  "intervals": [
    {
      "supplierId": "sup_01kv60qgnef2kt3pvqgwmkbzfr",
      "startUtc": "2026-07-15T14:00:00.000Z",
      "endUtc": "2026-07-15T15:00:00.000Z",
      "bookingTz": "America/Toronto",
      "locationType": "TRAVEL_ZONE",
      "locationId": "stz_01kv60qgs4e4nbjhzradnqtj0h",
      "latitude": 43.6532,
      "longitude": -79.3832,
      "address": {
        "addressOneLine": "100 Queen St W, Toronto, ON M5H 2N2, Canada",
        "streetNumber": "100",
        "streetName": "Queen St W",
        "city": "Toronto",
        "state": "ON",
        "country": "CA",
        "zipCode": "M5H 2N2"
      }
    }
  ]
}
```

An interval without `bookingTz` or `locationType` is now a `400 VALIDATION_ERROR`. This applies to the heartbeat too — extending a hold re-sends the same `intervals`, so they must carry the same fields.

**Why**

Convert rebuilds the booking from the **reservation alone** — never by re-reading a slate that may have expired while the client was paying. A hold that carried only a `locationId` could not say whether that id was a `Location` (`loc_…`) or a supplier travel zone (`stz_…`), so converting a mobile / in-home hold failed with `404 Location stz_… not found`, and a `TRAVEL_ZONE` booking's mandatory coordinates and address were never held at all. Travel-zone checkouts now work end to end.

**New**

- **`POST /holds`** — hold supplier time with `intervals` (single session or any explicit time), `slateId` (a whole package slate), or `slotIds` (a subset). All-or-nothing, in one transaction. Pass `reservationId` to **extend** an existing hold: the checkout heartbeat pushes `heldUntil` out and returns the same `reservationId` instead of minting a second hold.
- **`POST /holds/{reservationId}/convert`** — one idempotent endpoint for both shapes; it branches on the order item's `skuType` (`SINGLE_SESSION` books the one held interval; `PACKAGE` books every held interval and draws down credits). Safe to call straight from a Stripe webhook.
- **`GET /holds/{reservationId}`** and the `201` from `POST /holds` now **echo the full interval shape** — `bookingTz`, `locationType`, `locationId`, `latitude`, `longitude`, `address` — so you can verify exactly what convert will build.
- **`POST /holds/{reservationId}/release`** — free the time immediately when a checkout is abandoned. Idempotent, never an error.
- **Occupancy guard** — `409 SLOT_HELD` / `SLOT_BOOKED` on any write that collides with a live claim. The body names the blocking `reservationId` or `bookingId` and tells you what to do with it.
- **Conflict responses now carry the full error envelope.** Every `409` conflict and hold-lifecycle body (`SLOT_HELD`, `SLOT_BOOKED`, `HOLD_EXPIRED`, `RESERVATION_*`, and the slate codes) now includes `statusCode` and `requestId` alongside `code` and `message`, matching every other error. Purely additive — nothing was removed or renamed. If you were branching on the HTTP status because `body.statusCode` was missing on these, you no longer have to. See [Errors](/concepts/errors).

**What this means for you**

- If you build `intervals` by hand, **add `bookingTz` and `locationType` before your next deploy** — including in your heartbeat call.
- If you hold by `slateId` or `slotIds`, **nothing changes**: the slate's slots already carry every location field, and the hold now copies them onto the reservation for you.
- If you hold time, you must **convert** it — `POST /bookings` and `POST /orders/{orderId}/package-bookings` will not consume a hold, not even your own, and return `409 SLOT_HELD` naming your own `reservationId`.

Full walkthrough, a travel-zone worked example, and a status/code troubleshooting table: [Hold slots during checkout](/guides/hold-slots-for-checkout). The guard itself: [Concurrency](/concepts/concurrency).

## Catalog management endpoints

You can now manage your service catalog directly through the API. This release adds full create, read, update, and delete (CRUD) support for services, their offerings, and the business models attached to them — so you can build, sync, and automate catalogs without using the dashboard.

**New**

- **Services** — Create, list, retrieve, update, soft-delete, and toggle status for services on a project. See [Services](/api-reference/introduction).
- **Offerings** — Add offerings to a service, list them, fetch a single offering, update or soft-delete it, and change its status.
- **Business models** — Attach pricing/business models to a service, list them, update them, and toggle active status.

**What this means for you**

- Sync your catalog from an external system of record on a schedule.
- Build admin tooling that lives outside the MarketBox dashboard.
- Programmatically enable or disable offerings as inventory and availability shift.

All new endpoints are project-scoped and follow the existing [authentication](/concepts/authentication), [pagination](/concepts/pagination), and [error](/concepts/errors) conventions. Browse the full list under [API reference → Endpoints](/api-reference/introduction).
