title: Orders

An **order** in MarketBox is the commerce ledger sitting alongside the
booking ledger. It records what a client is paying for: line items
referencing offerings, with frozen unit prices and a tax field.

Where a booking answers "what's scheduled?", an order answers "what's
owed?".

## The order lifecycle

```
DRAFT ◄──► PENDING ══► PAID
  │           │          │
  └───────────┴──────────┴──► CANCELLED
```

`POST /v1/projects/{projectId}/orders/{orderId}/status` moves an order along
the single arrows:

- `DRAFT` → `PENDING`, `CANCELLED`
- `PENDING` → `DRAFT`, `CANCELLED`
- `PAID` → `CANCELLED`
- `CANCELLED` → nothing. Cancellation is terminal, so issue a new order
  instead.

Any other transition is a `400 BAD_REQUEST`.

**You cannot request `PAID`.** An order becomes `PAID` (the double arrow) when
its ledger covers its total, in the same write that records the money. See
[Settling an order](#settling-an-order). Asking for `PAID` is a `409`, and
retrying will not help:

```json
{
  "code": "ORDER_NOT_SETTLED",
  "message": "Order ord_01kx16f2a0h8a2my9u3f4tv0sp cannot be marked PAID by hand. Record a payment (or a comp) instead; the order becomes PAID when the ledger covers its total.",
  "statusCode": 409,
  "requestId": "0f3b8d2e-6a1c-4e97-b5d4-8c2a7e9f1b36"
}
```

A `409 VERSION_CONFLICT` from the same route still means the order changed
underneath you: re-read it and decide again.

`DELETE /v1/projects/{projectId}/orders/{orderId}` is a **soft-delete** —
the order is hidden from lists but its data is retained.

## Anatomy

An order is two things stored together:

- **The order**: client, currency, locale, tax, status, totals, audit metadata.
- **The items**: line-by-line, each referencing one offering with a
  frozen `unitPrice` and a `quantity`.

Fetch both in one call:

```
GET /v1/projects/{projectId}/orders/{orderId}/aggregate
```

## Currency is set once

When you create an order, you commit to a single currency. The currency
is **immutable** thereafter — there is no `PATCH` that changes it.

Every item added to the order must match the order's currency. The API
enforces this at add-item time and at create-time:

```json
{
  "code": "BAD_REQUEST",
  "message": "Item off_xxx currency EUR does not match order currency USD",
  "statusCode": 400,
  "requestId": "c8e4a1f6-3d9b-4c58-a207-9e5c1b7d4a68"
}
```

This rule eliminates the order/item currency desync that plagues most
naive commerce schemas.

`locale` follows the same rule: set at create, immutable thereafter.

<Note>
An item's `unitPrice` is resolved from the offering's (or package's)
regional price rules against the order's region, not from a single fixed
price — a mismatch here more often means the order didn't resolve the
region you expected than that the price data is wrong. See
[Regional pricing](/concepts/regional-pricing).
</Note>

## Creating an order

`POST /v1/projects/{projectId}/orders`. Optionally pass one region source —
`reservationId`, `locationId`, or `address` — so items price against the
right regional rule instead of falling back to the client's default address
or the `DEFAULT` rule; see [Regional pricing](/concepts/regional-pricing):

```json
{
  "clientId": "cli_456",
  "currency": "USD",
  "locale": "en-US",
  "locationId": "loc_01kx16f2a0h8a2my9u3f4tv0sp",
  "items": [
    {
      "skuType": "SINGLE_SESSION",
      "serviceId":  "srv_...",
      "offeringId": "off_...",
      "quantity": 1
    }
  ]
}
```

You can also create an order with `items: []` and add items afterwards.

Pass `locale` — the language the buyer completed the purchase in, typically the
language segment of your storefront URL — and MarketBox records it three times:
on the order, as a snapshot on every booking this order funds, and as the
client's `defaultLocale` (latest booking wins). It is normalized to canonical
BCP-47 on write, so `en-us` is stored as `en-US`; a tag that is not
`language[-Script][-REGION]` is a `400 VALIDATION_ERROR`. You do not send it on
`POST /bookings` — the booking copies it from the order. The recorded values
drive the `{clientLocale}` and `{bookingLocale}` tokens in your review-page
URL; see [Emails](/concepts/emails#where-the-rating-links-go).

The server pulls each offering's current price into the item as the
frozen `unitPrice`. From then on, the line's price is decoupled from
the offering — if the offering's price changes later, existing order
items keep the price they were captured at.

The server validates:

- Every offering exists and is `ACTIVE` (else 404 / 400).
- Every offering's currency equals the order's currency (else 400).
- `clientId` belongs to this project. A client from another project is a
  `404 NOT_FOUND`, and nothing is written.
- The service is sold the way the line implies. A `SINGLE_SESSION` line needs
  an active `SINGLE_BOOKING` rate on the service; a `PACKAGE` line needs an
  active `PACKAGE` or `SCHEDULED_PACKAGE` rate. Otherwise the order is refused
  with a `422`. The same check runs on `POST .../orders/{orderId}/items`:

```json
{
  "code": "SERVICE_NOT_SOLD_AS",
  "message": "Service srv_01kv60qg12e82acr78edfnjhvv is not sold as a single booking; it has no active SINGLE_BOOKING rate",
  "statusCode": 422,
  "requestId": "7c1e4b9a-2d53-4f08-a6e1-3b9d0c5f2a71"
}
```

Previously such a line was written with no rate attached, and so priced without
the rate's fees. Activate the rate in the MarketBox console, or sell the service
another way.

Each item carries `priceSource`. `RULE` means the `unitPrice` came from the
offering or package pricing rules (see `priceRuleId`). `MANUAL` means staff set
the price in the MarketBox console when they created the order, so
`priceRuleId` is null and `unitPrice` matches no rule. Items written before the
field existed have no `priceSource`.

## Managing items

Items have their own sub-resource under an order:

- `POST .../orders/{orderId}/items` — add an item. `unitPrice` is
  derived from the offering and snapshotted.
- `PATCH .../orders/{orderId}/items/{orderItemId}` — change
  **quantity only**. `skuType`, `serviceId`, `offeringId`, and the
  frozen `unitPrice` are immutable.
- `DELETE .../orders/{orderId}/items/{orderItemId}` — remove the
  item from the order.

The snapshot pattern is deliberate: an order is a historical record of
"what the client bought at the price it was when they bought it."

## How tax is computed

The platform computes tax. You never send a rate or a tax amount.

Each line takes its tax settings from the price rule it matched. When that rule
sets no tax, the line inherits from the rule's parents, most specific first:
`STATE`, then `COUNTRY`, then `DEFAULT`. When no rule sets tax, the line uses
the service's own `taxSettings`. The result is frozen on the line as
`taxSnapshot`.

`PACKAGE` lines are taxed by the same rule as every other line. Package lines
written between June and September 2026, while package purchases were
untaxed, keep their zero tax.

A line with no tax says why in `taxExemptReason`:

| Value | Meaning |
| --- | --- |
| `NO_RATE` | Neither the matched price rule, its parent rules, nor the service set a rate. |
| `NOT_TAXABLE` | The resolved tax settings mark the line not taxable. |
| `ZERO_RATE` | Taxable at 0%. |
| `MIGRATED_V1` | Imported from MarketBox v1, which recorded tax on the order rather than per line. |
| `PACKAGE_EXEMPT_LEGACY` | A package line written while package purchases were untaxed (June–September 2026). |

`taxExemptReason` is absent when the line is taxed at a positive rate. It is
also absent on lines written before the field existed. Treat the list as open:
new values can be added.

The order's tax is the sum of its line tax plus the tax on any taxable service
fee. See [Service fees](/concepts/service-fees) for how a fee is taxed.

## Updating an order

`PATCH /v1/projects/{projectId}/orders/{orderId}` changes nothing you can set.
Client, currency and locale are fixed. To change them, cancel the order and
create a new one. Change the line items to change the total.

`tax` is not editable. The platform recomputes it when the order is created and
whenever its lines change. The body still accepts `tax` for compatibility, but
only when it equals both the tax the lines compute and the tax the order
stores. Omit it.

Any other figure is refused, and nothing is written:

```json
{
  "code": "TAX_MISMATCH",
  "message": "tax 2000 CAD disagrees with order ord_01kv8m3n5p7q9r1s3t5v7w9x1z: its lines compute 2600 CAD and it stores 2600 CAD. Omit tax — the platform computes it from the line items.",
  "statusCode": 400,
  "requestId": "5b8e2d41-7c9a-4f13-b6e0-9a2c4d7f1e38"
}
```

The same `400 TAX_MISMATCH` is returned when you send `tax` on an order whose
lines are in a different currency from the order. The `message` then names
both currencies.

On an order whose stored tax no longer matches its lines, no figure passes.
That is deliberate: rewriting tax on a paid order could drop its total below
what was already paid.

## Settling an order

The ledger is the source of truth for money. An order's `amountPaid`,
`amountComped`, `paymentMethod`, `settledAt` and `PAID` status are all derived
from its transactions. An order moves from `DRAFT` or `PENDING` to `PAID` when
`amountPaid` plus `amountComped` covers `total`.

Money reaches the ledger in two ways:

- **Cards** go through the payment-intent flow and settle when Stripe's webhook
  arrives. See [Accept payments with Stripe](/guides/accept-payments-with-stripe).
- **Cash, bank transfers and comps** are recorded with
  `POST /v1/projects/{projectId}/orders/{orderId}/transactions`.

```json
{
  "kind": "PAYMENT",
  "source": "CASH",
  "amount": { "amount": 4500, "currency": "CAD" },
  "idempotencyKey": "9f8c0f7a-1f3f-4c8e-9a2b-6c7d8e9f0a1b"
}
```

A recording that covers the balance moves the order to `PAID` in the same
write, and stamps two fields on it:

| Field | Meaning |
| --- | --- |
| `paymentMethod` | How the order was settled: `STRIPE`, `CASH`, `EXTERNAL`, `COMP`, `MIXED` (more than one source contributed), or `LEGACY` (migrated from MarketBox v1 with no settling ledger rows). Absent until the order is `PAID`. |
| `settledAt` | The instant the money that completed the order was recorded — your "cash received" date. |

`amountComped` totals the comps on the order. Treat it as zero when absent.

Two rules on the transaction body:

- **`source: "COMP"` requires `reason`**, 1–500 characters. Record why the
  charge was waived, such as `"Service recovery — late supplier"`. A comp with
  no reason is a `400`.
- **Send `idempotencyKey` on any recording you might retry.** A first recording
  returns `201` with `replayed: false`. The same key on the same order returns
  the row the first call created, as `200` with `replayed: true`, and records
  nothing. Branch on the status or on `replayed`, never on "any 2xx means I
  just took a payment". A key belongs to one order and does not expire.

A `409 TRANSACTION_IDEMPOTENCY_RECORD_MISSING` means the key matched an earlier
recording whose row could not be read back. It is terminal. Do not retry it.
Re-read the order's transactions and contact support with the `requestId`.

Every transaction also carries `channel`, the path that wrote it (`OPEN_API`
for your key, `BACKOFFICE`, `STRIPE_WEBHOOK`, and others), and `reason`.

## Listing orders

| Endpoint                                                     | Notes                                              |
| ------------------------------------------------------------ | -------------------------------------------------- |
| `GET /v1/projects/{projectId}/orders`                        | One of three listing modes, chosen by the filter you send. |
| `GET /v1/projects/{projectId}/clients/{clientId}/orders`     | All orders for one client (any status).            |

`GET /v1/projects/{projectId}/orders` answers exactly one question per request:

| Send | Lists | Narrow with |
| --- | --- | --- |
| `status` | Orders in that status. | `startCreatedAt`, `endCreatedAt` |
| `paymentMethod` | Settled orders, by how they were paid. `DRAFT` and `PENDING` orders never appear. This is the reconciliation read: "what did we take in cash last month?" | `startSettledAt`, `endSettledAt` |
| Neither | Every order. | `startCreatedAt`, `endCreatedAt` |

Start bounds are inclusive. End bounds are **exclusive**, so pass the next
period's start to cover a whole month:

```bash
curl "$MARKETBOX_API_URL/v1/projects/$MARKETBOX_PROJECT_ID/orders?paymentMethod=CASH&startSettledAt=2026-09-01T00:00:00.000Z&endSettledAt=2026-10-01T00:00:00.000Z" \
  -H "x-api-key: $MARKETBOX_API_KEY"
```

Each of these is a `400`:

- Sending both `status` and `paymentMethod`.
- Sending `startSettledAt` or `endSettledAt` without `paymentMethod`.
- Sending `startCreatedAt` or `endCreatedAt` with `paymentMethod`.
- Replaying a `cursor` after switching listing mode. A cursor belongs to the
  filters that produced it, so start a fresh request instead.

<Warning>
  **The no-filter mode is incomplete for older orders.** It reads an index that
  is written only when an order is created. Orders created before this listing
  mode shipped, and orders migrated from MarketBox v1, are missing from it until
  a backfill runs. An empty or short result there does not mean the project has
  no orders. List by `status` when you need every historical order.
</Warning>
