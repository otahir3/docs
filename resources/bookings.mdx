---
title: Bookings
description: Create, manage, and operate on bookings — the core scheduling primitive.

A **booking** is the central scheduling primitive in MarketBox. It pins
a `supplier` and a `client` to a window of time, against one or more
service offerings, with optional notes and participants.

## The booking lifecycle

A booking is created as `SCHEDULED` and settles into one of the outcomes
on the right. The middle column is where the platform decides what happened
after the session ended.

```
SCHEDULED ──► STARTED ──► AWAITING_CONFIRMATION ──► COMPLETED
    │            │                 │                CLIENT_NO_SHOW
    │            │                 └──► DISPUTED ──► SUPPLIER_NO_SHOW
    └────────────┴──────────────────────────────────► CANCELLED
```

`status` on every booking response is one of nine values:

| Status | Meaning | Who puts a booking here |
| --- | --- | --- |
| `SCHEDULED` | Created, not yet started. The only start state. | Booking creation. Nothing transitions *into* it. |
| `STARTED` | The session is under way. | Your key, or the supplier, once `bookingStartUtc` has passed. |
| `AWAITING_CONFIRMATION` | The session has ended and MarketBox is waiting on the two parties' attendance reports. | The platform, when `bookingEndUtc` passes. An operator can also reverse a settled booking back here within a window. |
| `DISPUTED` | The client and supplier reported different things about attendance. | The platform only. Resolved by an operator in the MarketBox console. |
| `COMPLETED` | Delivered. | The platform (both attended, or the confirmation window timed out), or your key. |
| `CLIENT_NO_SHOW` | The client did not attend. | The platform (from the supplier's report), your key, or the supplier — after a grace period past the start. |
| `SUPPLIER_NO_SHOW` | The supplier did not attend. | The platform (from the client's report), your key, or the client — after the same grace period. |
| `CANCELLED` | Called off. **Hard-terminal**: money may have moved, so nothing leaves this state. | Your key, or either party, before `bookingEndUtc`. |
| `NO_SHOW` | **Legacy, read-only.** The pre-split no-show, which does not say which side was absent. Nothing transitions out of it. | Nothing, any more. Bookings recorded before the split keep it indefinitely. |

You move a booking with
`POST /v1/projects/{projectId}/bookings/{bookingId}/status`. The request
body's `status` enum is narrower than the response's: `SCHEDULED` and
`DISPUTED` can be observed but never requested, so they are not in it.

<Note>
  **What an API key may do.** A key carries every transition an operator
  has, except the ones that need a human to decide between two accounts of
  what happened: it cannot resolve a `DISPUTED` booking, and it cannot
  reverse a settled booking (`COMPLETED`, `CLIENT_NO_SHOW`,
  `SUPPLIER_NO_SHOW`) back to `AWAITING_CONFIRMATION`. Both are reserved for
  the MarketBox console. Which transitions are open also depends on the
  clock — a booking cannot be started before `bookingStartUtc`, or marked a
  no-show until a grace period after it.
</Note>

A transition the booking cannot make from where it stands is a
`400 BAD_REQUEST` whose `message` names the booking's **current** status, so a
rejection tells you what to retry from. `409 VERSION_CONFLICT` means the
booking changed underneath you — re-read it and decide again. See
[Errors](/concepts/errors).

### `NO_SHOW` can no longer be set

Send `CLIENT_NO_SHOW` or `SUPPLIER_NO_SHOW` to record which side was absent.
Sending `NO_SHOW` is a `400` whose `message` names the value.

`NO_SHOW` is still a status a booking can **carry**. Bookings recorded before
the split keep it and are not being migrated, because nobody recorded which
party failed to show. If you switch exhaustively on `status`, keep a case for
it.

### Cancelling and the package credit

Send `status: "CANCELLED"` to cancel. In the same atomic write, MarketBox
releases the supplier's time and settles the order item the booking drew on.
What happens to the session depends on the order item:

| Booking drew on | Default outcome | `creditTreatment` |
| --- | --- | --- |
| A `PACKAGE` order item | The session goes back to the order item: `quantityRemaining` rises and a `CREDIT_REVERSAL` transaction offsets the original `CREDIT_REDEMPTION`. | Send `"FORFEIT"` to keep the session spent, for example for a late cancellation. `"RETURN"` states the default explicitly. |
| A `SINGLE_SESSION` order item | The allocation is closed. No quantity comes back, because a single session holds no reusable credit. | Don't send it. It is a `422 NO_SESSION_CREDIT`, and nothing is cancelled. |

```json
{
  "status": "CANCELLED",
  "cancellationReason": "Client called the morning of the session",
  "creditTreatment": "FORFEIT"
}
```

`creditTreatment` is only valid with `CANCELLED`. The status route never moves
money: a forfeited session is not refunded, and a returned one is not charged
again.

The cancellation email to the client reports what happened to their session
credit. It does not include your `cancellationReason` text, which stays on the
booking.

Every booking response now carries the cancellation record, when there is one:

| Field | Meaning |
| --- | --- |
| `creditTreatment` | What was decided about the session credit: `RETURN`, `FORFEIT`, `REFUND_ORIGINAL_PAYMENT`, or `NOT_APPLICABLE` (the booking held no package credit). Absent on bookings cancelled before this field existed. |
| `cancellationInitiatedBy` | `CLIENT`, `SUPPLIER` or `BUSINESS`, when the cancellation recorded it. |
| `cancellationReasonCode` | A reportable reason, such as `WEATHER` or `BOOKED_IN_ERROR`, when the cancellation recorded one. |

`REFUND_ORIGINAL_PAYMENT`, `cancellationInitiatedBy` and
`cancellationReasonCode` are set by cancellations made in the MarketBox
console. You can read them, but the public API does not set them.

Every booking also records who last moved it. `statusUpdatedAt` is the
instant, `statusUpdatedBy` is the actor, and `statusUpdatedByCapacity` is one
of `ADMIN`, `SUPPLIER`, `CLIENT`, `SYSTEM` or `API`. A change made through
the public API is attributed to the **API key** that made it, in the `API`
capacity — the key is what gets rotated or revoked, so "which key did this"
is the question an incident asks.

A booking is **soft-deleted** with
`DELETE /v1/projects/{projectId}/bookings/{bookingId}`. Soft-deleted
bookings disappear from list endpoints but their data is retained for
audit purposes. Reserve delete for bookings created in error; cancel a booking
that was genuinely called off.

A delete settles the booking exactly like a default cancel: it releases the
supplier's time, returns a package session to its order item, and closes a
single-session allocation. Deleting a booking that is already `CANCELLED`
leaves that cancel's settlement as it stands.

## Anatomy

A booking has three nested collections beyond its own metadata:

<CardGroup cols={3}>
  <Card title="Services" icon="briefcase">
    The offerings booked — each line carries the offering snapshot,
    quantity, duration, and price at the time the booking was made.
  </Card>
  <Card title="Participants" icon="users">
    The clients attending. Used for group/class-style bookings with
    capacity above 1. Supports check-in.
  </Card>
  <Card title="Notes" icon="note-sticky">
    Free-form notes scoped to either the booking or one of its
    services. Soft-deletable.
  </Card>
</CardGroup>

Fetch all three in one call with the **aggregate** endpoint:

```
GET /v1/projects/{projectId}/bookings/{bookingId}/aggregate
```

This is the right call for "show me everything about this booking" —
one round trip instead of four.

## Creating a booking

`POST /v1/projects/{projectId}/bookings` creates a booking and its
services in one transaction. The body carries:

- **`supplierId`** and **`clientId`** — who serves and who is served.
- **`bookingStartUtc`**, **`bookingEndUtc`**, **`bookingTz`** — when.
  Local-time fields are derived. See [Timezones](/concepts/timezones).
- **`capacity`** — how many participants this booking can hold (1 for
  one-to-one bookings; >1 for classes).
- **`services`** — at least one service line. Each line names a
  `serviceId` + `offeringId`; price and duration are pulled from the
  offering at create time and **snapshotted** into the booking.
- **`notes`** — optional initial notes.

The server validates:

- `bookingEndUtc > bookingStartUtc`.
- Every referenced offering exists and is `ACTIVE` (otherwise 400).
- All service lines share a single currency (otherwise 400).
- `bookingTz` is a valid IANA identifier.
- `clientId` and `supplierId` belong to this project. An id from another
  project is a `404 NOT_FOUND`, exactly as if it did not exist, and nothing is
  written. The same check applies to `supplierId` on `PATCH`, to `clientId` on
  `POST .../participants`, and to the ids on order create, package bookings,
  holds and manual transactions.
- A line that draws on an order item names a `businessModelType` that item is
  sold as: a `SINGLE_SESSION` item books as `SINGLE_BOOKING`, a `PACKAGE` item
  as `PACKAGE` or `SCHEDULED_PACKAGE`. Anything else is a
  `400 ORDER_ITEM_BUSINESS_MODEL_MISMATCH`:

```json
{
  "code": "ORDER_ITEM_BUSINESS_MODEL_MISMATCH",
  "message": "Order item oi_01kx16f2a0h8a2my9u3f4tv0sp is a SINGLE_SESSION line and can only be booked as SINGLE_BOOKING, not PACKAGE",
  "statusCode": 400,
  "requestId": "5b0e6a2c-8f41-4d7e-9c3a-2e6d1f0b7a94"
}
```

<Note>
  **Note fan-out is non-atomic.** If a note write fails after the
  booking is created, the booking still exists with fewer notes than
  requested, and the error propagates to you. Retry the note creation
  against the existing `bookingId`.
</Note>

<Note>
  **`locale` is derived, not sent.** A booking carries `locale`, the language
  the funding order was placed in, copied from the order at create time —
  through `POST /bookings`, `POST /orders/{orderId}/package-bookings` and hold
  conversion alike. It is a snapshot: a client who books in `fr-CA` and later in
  `en-US` keeps `fr-CA` on the first booking, so a review link mailed nine days
  later still lands on the right page. Absent when the order had none. Set it on
  the order — see [Orders](/resources/orders#creating-an-order).
</Note>

## Rescheduling

`PATCH /v1/projects/{projectId}/bookings/{bookingId}` updates time and
core fields. The body may include any subset of:

- `bookingStartUtc`, `bookingEndUtc`, `bookingTz`
- `supplierId`, `clientId`
- `capacity`

You cannot send the four `bookingLocal*` fields or `locale` — they're
server-derived.

If you change any time field, the server recomputes all four local
fields against the (possibly new) `bookingTz`.

A booking whose length deliberately differs from its service's duration carries
`durationOverrideMinutes` and `durationOverrideReason`. Staff set them in the
MarketBox console, and `bookingEndUtc` already reflects the override. Absent is
the normal case: the booking runs as long as its service says.

## Listing bookings

Three list endpoints — all paginated, all returning `BookingDto`:

| Endpoint                                                     | Scope                                    |
| ------------------------------------------------------------ | ---------------------------------------- |
| `GET /v1/projects/{projectId}/bookings`                      | All bookings in a project.               |
| `GET /v1/projects/{projectId}/suppliers/{supplierId}/bookings` | Bookings assigned to one supplier.       |
| `GET /v1/projects/{projectId}/clients/{clientId}/bookings`   | Bookings owned by one client.            |

All three accept the same query params: `startDate`, `endDate`,
`status`, `limit`, `cursor`.

`startDate` / `endDate` are **UTC** windows. See
[Timezones](/concepts/timezones) for how to convert from a local
window.

## Participants

Group bookings (`capacity > 1`) support a participant list:

- `POST .../bookings/{bookingId}/participants` — register a client.
  409 if capacity is full or the client is already on the list.
- `GET .../bookings/{bookingId}/participants` — list the current
  roster. Not paginated — bounded by capacity.
- `POST .../bookings/{bookingId}/participants/{clientId}/check-in` —
  mark a participant as checked in.
- `DELETE .../bookings/{bookingId}/participants/{clientId}` — cancel
  the participant (soft-delete; capacity recovers).

## Notes

Notes are attached at one of two scopes:

| Scope                | When to use                                                   |
| -------------------- | ------------------------------------------------------------- |
| `BOOKING`            | Applies to the whole booking. Set `bookingServiceId: null`.    |
| `BOOKING_SERVICE`    | Applies to one service line. Set `bookingServiceId: <id>`.    |

CRUD lives under `.../bookings/{bookingId}/notes[/{noteId}]`. The list
is not paginated — it's bounded by what fits in the aggregate.
