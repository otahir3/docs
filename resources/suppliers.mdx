---
title: Suppliers
description: The people or units that fulfill bookings in a project, and the two endpoints that describe them.
---

A **supplier** is the entity that fulfills a booking — typically a person, but
conceptually any unit of capacity (a stylist, a doctor, a tutor, a meeting room).

There are two ways to read one, and picking the right one matters:

| You are building | Call | You get |
| --- | --- | --- |
| A directory or picker | `GET /v1/projects/{projectId}/suppliers` | A page of suppliers, each with services, skills and locations |
| One supplier's profile page | `GET /v1/projects/{projectId}/suppliers/{supplierId}` | The same shape, **plus** the supplier's rating and working hours |

The detail endpoint is a superset. The list omits `rating` and `availability`
on purpose — each costs an extra read per supplier, and a 200-row page should
not pay for data a directory does not show.

## Booking identity

A supplier response is not just display content. These are the fields you need
to actually book against a supplier, and where each one lives:

| What you need | Field | Notes |
| --- | --- | --- |
| Stable supplier id | `supplierId` | Send as `supplierId` when creating a booking or a hold. |
| Whether they take bookings | `active` | See the warning below — `active: true` alone does not mean bookable. |
| What they can deliver | `services[].serviceId` + `services[].name` | Ids to book with, and localized labels to render. |
| Timezone | `timezone` | Their own IANA zone. May be absent — see [Timezone](#timezone). |
| Where they work | `locations[].locationId` | Includes travel zones. This is the id you send as `locationId`. |
| Regions served | `servedRegions` | The exact set the list's `country`/`state`/`city` filter matches against. See [Regions served](#regions-served). |
| Country and market | `country`, `state`, `postalcode` | The inputs [regional price rules](/concepts/regional-pricing) resolve against. |
| Public profile | `firstName`, `lastName`, `bio`, `avatarUrl`, `languages`, `locales` | Everything a card renders. |
| Reputation | `rating.averageRating`, `rating.reviewCount` | Detail endpoint only. |
| Working hours | `availability.schedules[]` | Detail endpoint only. **Not** bookable times. |

<Warning>
  `active` and bookability are set independently. A supplier can be `active:
  true` and still be impossible to book, because they have no live schedule.
  The reliable check is `availability.schedules.length > 0`, and the only
  authoritative one is asking the availability engine for real times.
</Warning>

## Anatomy

Every supplier response — list row or detail — carries these.

**Profile fields**, selected from the full supplier record:

| Field | Notes |
| --- | --- |
| `supplierId` | Stable identifier. |
| `firstName`, `lastName` | Display name. |
| `email`, `phone` | Contact details. `phone` is stored as E.164 (`+14165550134`) for any supplier created or edited through the API since September 2026; rows that predate that hold whatever was typed until they are next edited. |
| `addressoneline`, `city`, `state`, `country`, `postalcode` | Address. Note the lowercase spelling of `addressoneline`. |
| `longitude`, `latitude` | Geolocation for travel-time logic. |
| `timezone` | IANA timezone. Absent when unset on the profile. |
| `bio` | Free-form bio text. |
| `avatarUrl` | Ready-to-use image URL, or `null` when no avatar is set. |
| `languages` | ISO 639-1 codes the supplier speaks, e.g. `["en","fr"]`. |
| `locales` | Server-derived from `languages` × `country`, e.g. `["en-CA","fr-CA"]`. |
| `defaultLocale` | The supplier's own preferred locale, BCP-47 (`fr-CA`). Staff-set, never inferred from a booking. **Absent when unset** — fall back to your project default. One tag, unlike the derived `locales` array. |
| `maxTravelTime` | For mobile suppliers — maximum travel time they will accept, in minutes. |
| `active` | Whether the supplier is taking bookings. |
| `externalId`, `externalData` | Pass-through fields for your own ids and metadata. |
| `updatedAt` | Last modification timestamp. |

**Enriched mappings**, joined against the project's catalog and schedules:

| Field | Shape |
| --- | --- |
| `services` | Array of `{ serviceId, name: { en, fr, … } }`. |
| `skills` | Array of `{ skillId, name: { en, fr, … } }`. |
| `locations` | Array of location records. See [Locations](#locations). |
| `servedRegions` | Array of slug region paths, e.g. `["ca/","ca/on/","ca/on/toronto/"]`. See [Regions served](#regions-served). |

Both `services` and `skills` carry **localized name maps**. If your project's
services are named in several languages, the response contains all of them —
pick the locale you want client-side.

<Note>
  Only bookable catalog is joined in. A mapping to a service that is not `LIVE`,
  or to an inactive skill, is **dropped from the array entirely** rather than
  returned with a blank name. So `services` is what this supplier can actually
  be booked for today, not a historical record of what they were ever assigned.
</Note>

## Timezone

`timezone` is the supplier's own IANA zone, and it is **optional on the
profile** — a project whose suppliers all work in one place often leaves it
unset.

The list endpoint returns it as-is, absent and all. The detail endpoint
additionally resolves it for you:

```json
"availability": {
  "timezone": "America/Toronto",
  "timezoneSource": "SUPPLIER"
}
```

`timezoneSource` tells you whether that value is real. `SUPPLIER` means it came
from the profile. `PROJECT` means the profile had none and the project default
was substituted — a sensible display default, but not a statement about where
this supplier works. Do not derive travel logic from a `PROJECT`-sourced zone.

See [Timezones](/concepts/timezones) for how booking times are rendered.

## Locations

The `locations[]` array is **derived from the supplier's schedules** — not
stored on the supplier record. A location nobody is scheduled at is not
somewhere you can book, so it does not appear.

Each schedule contributes locations through three reference shapes:

| Source on the schedule | Resolves against |
| --- | --- |
| `locationRefs[]` | Locations |
| `physicalLocationIdsInsideTravelZone[]` | Locations |
| `travelZoneRef` | The schedule's own travel zone |

Locations are **deduped by `locationId`**. References that do not resolve (a
deleted location, a missing travel zone) are skipped silently rather than
surfaced as nulls.

Each location record:

| Field | Notes |
| --- | --- |
| `locationId` | Stable identifier. For a supplier-owned travel zone this is the `stz_` id. |
| `locationType` | `PHYSICAL`, `VIRTUAL`, or `TRAVEL_ZONE`. |
| `name` | Display name. |
| `country`, `state`, `city`, `street`, `addressOneLine` | Address fields. Any may be `null`. |
| `latitude`, `longitude` | Geolocation. May be `null`. |
| `travelZoneType` | `CIRCULAR` or `DRAWN`. Only set on `TRAVEL_ZONE` locations. |

Only **live** schedules contribute. A schedule is live when it is `ACTIVE`, not
deleted, and its `endDate` has not passed in the schedule's own timezone. That is
the same rule the list's region filter, `servedRegions` and the detail endpoint's
`availability.schedules` use, so the four never disagree about whether a
supplier can be booked. A supplier with no live schedule has `locations: []` —
including one whose only schedule ended last week.

## Regions served

`servedRegions` is the answer to "why is this supplier (not) returned by
`country=CA&state=ON&city=Toronto`?". It is the list of region paths the
supplier is indexed under — the **same set** the list's location filter
matches against, so a supplier is returned by that filter exactly when the
query's path is in this array.

```json
"servedRegions": ["ca/", "ca/on/", "ca/on/scarborough/", "ca/on/toronto/"]
```

- Slug paths at **every level** of the hierarchy, sorted. A zone in Toronto
  contributes `ca/`, `ca/on/` and `ca/on/toronto/`, so `country=CA` alone
  matches it.
- Derived from the travel zones and physical locations on the supplier's
  **live** schedules — the same sources as `locations[]`.
- A zone inside a borough is indexed under the locality, the borough **and**
  the wider municipality. A Scarborough zone carries both
  `ca/on/scarborough/` and `ca/on/toronto/`, so `city=Scarborough` and
  `city=Toronto` both return it.
- `[]` when the supplier has no live schedule with a geocodable zone.

<Note>
  `locations[]` is evaluated on every request; `servedRegions` is maintained by
  an index that a daily sweep prunes. For up to a day after a schedule's
  `endDate` passes, a supplier can therefore still carry the region in
  `servedRegions` (and still match the filter) while `locations[]` has already
  dropped it. Treat `locations[]` as the fresher of the two.
</Note>

## Rating and reviews

`rating` is read from an aggregate maintained in the same atomic write that
records each review, so it never disagrees with the rows behind it.

| Field | Notes |
| --- | --- |
| `averageRating` | Mean stars, rounded to one decimal place. |
| `reviewCount` | How many reviews the average is based on. |
| `recent` | The five newest reviews, for a profile card. |

A supplier nobody has reviewed returns `averageRating: 0` and `reviewCount: 0`
— check `reviewCount` before rendering stars, or an unrated supplier displays
as a zero-star one.

`recent` is a **preview, not the full set**. To page through every review, call
`GET /v1/projects/{projectId}/reviews` with `supplierId`. See
[Reviews](/resources/reviews). No email address is returned for either party.

If the rating badge is all you need and you are not rendering a whole profile,
`GET /v1/projects/{projectId}/suppliers/{supplierId}/review-summary` returns
just the aggregate.

## Availability is a pattern, not a list of times

This is the single most expensive thing to get wrong on this endpoint.

`availability.schedules[]` describes **when and where this supplier works**. It
is the recurring pattern an operator configured. It knows nothing about:

- bookings already on the calendar,
- time off,
- how long the offering you want to sell actually takes.

So it cannot tell you a time is free. **Never present a time built from
`weeklyHours` as available.** For times you can genuinely book, call
`POST /v1/projects/{projectId}/availability/suppliers` with a service, an
offering and a location — see
[Search suppliers by availability](/guides/search-suppliers-by-availability).

What the pattern is good for: rendering "Mon, Wed 9–5" on a profile, deciding
whether to show a supplier at all, and telling a client the earliest week worth
asking about.

### Reading a schedule

| Field | Notes |
| --- | --- |
| `scheduleId` | Stable identifier. |
| `timezone` | The zone **this schedule's** times are in. Usually matches the parent `availability.timezone`, but a supplier working across zones can differ — always read against this one. |
| `startDate`, `endDate` | The window the schedule is in effect, `YYYY-MM-DD`. |
| `rrule` | Which weeks inside that window it runs. `FREQ=WEEKLY;INTERVAL=1` is every week, `INTERVAL=2` fortnightly. |
| `exdates` | Individual excluded dates — holidays, one-off closures. |
| `weeklyHours` | The working windows that repeat each covered week. |
| `appliesToAllOfferings` | When `true`, `offeringIds` is empty and the schedule covers everything. |
| `offeringIds` | The offerings covered. Empty means **all**, not none — read `appliesToAllOfferings` first. |
| `locationIds` | Fixed locations worked at. Each also appears in `locations[]` with its address. |
| `travelZone` | `{ locationId, source }`, or `null` for a fixed-location schedule. |
| `summary` | Pre-rendered English display strings. Not localized — build your own from the structured fields if you serve several locales. |

Two traps in `weeklyHours`:

- **The weekdays come from `weeklyHours`, not from `rrule`.** The rule decides
  which weeks; the array decides which days. A weekday absent from the array is
  a day this supplier does not work.
- **`crossesMidnight` must be checked before comparing times.** A night shift is
  `startTime: "22:00"`, `endTime: "02:00"`, `crossesMidnight: true`. Compare the
  two strings without it and you get a negative-length day.

`travelZone.source` distinguishes a zone drawn for this supplier alone
(`SUPPLIER_TRAVEL_ZONE`, an `stz_` id) from a project-wide zone several
suppliers share (`PROJECT_LOCATION`, a `loc_` id). Both are booked the same
way; the distinction only matters if you draw a coverage map.

Only **live** schedules are returned — `ACTIVE`, not deleted, and `endDate` not
yet passed in the schedule's own `timezone`. `schedules: []` means the supplier
cannot currently be booked at all, whatever `active` says.

## Listing suppliers

```
GET /v1/projects/{projectId}/suppliers
```

| Param | Default | Notes |
| --- | --- | --- |
| `limit` | 50 | Page size. Max 200. |
| `cursor` | — | Pagination cursor. See [Pagination](/concepts/pagination). |
| `services` | — | Comma-separated service ids. |
| `skills` | — | Comma-separated skill ids. |
| `country` | — | ISO 3166-1 alpha-2, e.g. `CA`. |
| `state` | — | ISO 3166-2, `CA-ON` or `ON`. Requires `country`. |
| `city` | — | Requires `country` and `state`. |
| `lat` | — | Latitude of a point to be covered, decimal degrees. Requires `lng`. |
| `lng` | — | Longitude of that point. Requires `lat`. |

Every filter is **AND**, both within a parameter and across them.
`services=srv_a,srv_b` means a supplier offering *both*, never either.

There are two ways to filter by place, and they are **exclusive**:

- **By region** — `country`, then `state`, then `city`. Hierarchical, and each
  level requires the one above: `state` without `country` is a `400`, as is
  `city` without both.
- **By point** — `lat` + `lng`, both or neither. Returns every supplier whose
  live travel zone **contains that point**, tested against the zone's actual
  polygon or radius rather than a place name, and AND-combined with
  `services`/`skills`.

Sending `lat`/`lng` together with any of `country`/`state`/`city` is a `400`.

```bash
# who covers this address in Scarborough?
curl "$MARKETBOX_API_URL/v1/projects/$MARKETBOX_PROJECT_ID/suppliers?lat=43.7462&lng=-79.2191&services=srv_01kv60qg12e82acr78edfnjhvv" \
  -H "x-api-key: $MARKETBOX_API_KEY"
```

<Note>
  Both filters match the regions a supplier **serves** — derived from the travel
  zones and physical locations on their **live** schedules — not the address on
  their profile. A mobile supplier based in Barrie whose travel zone covers
  Toronto matches `city=Toronto`. A supplier with an address but no live
  schedule matches nothing, because they cannot be booked. Coverage resolves to
  the locality, its borough and the wider municipality, so a Scarborough zone is
  returned by `city=Scarborough` and by `city=Toronto`. Each row's
  `servedRegions` is the exact list the region filter checked — see
  [Regions served](#regions-served).
</Note>

<Warning>
  A point only matches **travel zones**. A supplier whose live schedules are all
  at fixed locations has no zone and is never returned by `lat`/`lng`, even if
  the point is their own studio. Use the region filter, or
  `POST /v1/projects/{projectId}/availability/suppliers` with a `locationId`,
  for fixed-location suppliers.
</Warning>

Only active suppliers are listed; inactive and deleted ones never appear, on
any combination of filters. Results are ordered by supplier id, not by name.

Treat `nextCursor: null` as the **only** end-of-results signal — never stop on
a page that merely looks short. A cursor is valid only against the filter set
that produced it; change a filter mid-walk and restart.

## Managing suppliers

Supplier management is normally done in the MarketBox dashboard, but the public
API exposes it too, so you can keep a roster in sync from your own system:

| Operation | Endpoint |
| --- | --- |
| Create | `POST /v1/projects/{projectId}/suppliers` |
| Update | `PUT /v1/projects/{projectId}/suppliers/{supplierId}` |
| Soft-delete | `DELETE /v1/projects/{projectId}/suppliers/{supplierId}` |
| Add a service | `POST /v1/projects/{projectId}/suppliers/{supplierId}/services/{serviceId}` |
| Remove a service | `DELETE /v1/projects/{projectId}/suppliers/{supplierId}/services/{serviceId}` |
| Add a skill | `POST /v1/projects/{projectId}/suppliers/{supplierId}/skills/{skillId}` |
| Remove a skill | `DELETE /v1/projects/{projectId}/suppliers/{supplierId}/skills/{skillId}` |
| Get an avatar upload URL | `POST /v1/projects/{projectId}/suppliers/{supplierId}/avatar/upload-url` |
| Attach an uploaded avatar | `PUT /v1/projects/{projectId}/suppliers/{supplierId}/avatar` |
| Remove an avatar | `DELETE /v1/projects/{projectId}/suppliers/{supplierId}/avatar` |

Use `externalId` to carry your own primary key onto the supplier, so you can
reconcile without storing a second id map.

Two profile fields have write rules worth knowing:

| Field | On `POST` | On `PUT` |
| --- | --- | --- |
| `phone` | Optional. E.164 or a national NANP number (`(416) 555-0134`); stored as E.164 (`+14165550134`). Numbers outside North America must carry `+` and a country code. | Omit to keep, `null` to clear, anything else is validated and normalized. |
| `defaultLocale` | Optional BCP-47 tag (`fr-CA`), normalized (`fr-ca` is stored as `fr-CA`). Omit to inherit the project default. | Omit to keep, `null` to clear. |

An unparseable phone or a malformed locale is a `400 VALIDATION_ERROR` — the
row is not written. A `PUT` with `"phone": "(416) 555-0134"` reads back as
`"phone": "+14165550134"`.

Schedules are **not** writable through the public API. A supplier created here
has no schedule, so `availability.schedules` is `[]` and they cannot be booked
until an operator sets working hours in the dashboard.
